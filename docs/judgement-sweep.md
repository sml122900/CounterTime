# 판정식 전수 스윕 — 360조합 (2026-08-09)

`JudgementCalculator.Evaluate` 를 순수 Core 로 전수 호출했다. 랜덤·시나리오 안 탄다.

    잡기 5(−2..+2) × 읽기 4(−3/0/+2/+3) × 체력 3(0/+2/+3) × 기술급 3(0/1/2) × 수비자세 2(0/−2)
    = 360

체력 항은 값을 직접 넣지 않고 실제 체력값(100 / 30 / 10)을 넣어 `Evaluate` 가 항을
유도하게 했다 — 여기서 공식을 다시 쓰면 그게 두 번째 파생이 된다.

CSV 전체: `Temp/judgement-sweep.csv` (리포 밖, gitignore).

## 왜 이걸 했나

§8 은 "42노드 대조로 되치기 발화 조건의 분포를 본다"고 정해뒀는데, 대조 결과
**되치기 표본이 0** 이었다. 시나리오는 스크립트된 레퍼런스 매치지 표본 추출이 아니다.
판정식의 항이 유한하므로 전 조합을 계산하는 쪽으로 대체한다.

## 2. 되치기 (sum ≤ −3) — 31조합 / 360 = 8.6%

| 읽기 항 | 조합 수 |
|---|---|
| 읽힘(−3) 포함 | 28 |
| **읽기 ≥ 0 인데도 되치기** | **3** |

### ★ 읽히지 않고도 되치기가 나는 3조합

| 잡기 | 읽기 | 체력 | 기술급 | 수비자세 | 합 |
|---|---|---|---|---|---|
| −2 | 0 | 0 | 0 (엉성) | −2 | **−4** |
| −2 | 0 | 0 | 1 (정규) | −2 | **−3** |
| −1 | 0 | 0 | 0 (엉성) | −2 | **−3** |

**예상대로 존재한다.** 그리고 세 조합의 성질이 하나로 모인다:

- **셋 다 수비자세 −2 가 필수다.** 즉 되치는 쪽은 **카운터 준비를 선언한 게 아니라
  그냥 웅크리고 있던 상대**다.
- 셋 다 체력 항 0 — 상대가 지쳐서가 아니라 잡기 열세 + 허술한 기술 때문이다.
- 잡기 +0 이상에서는 읽기 ≥ 0 로 되치기가 절대 안 난다. 잡기 열세 전용이다.

⇒ **"되치기 = 카운터 준비 전용"이라는 전제는 성립하지 않는다.**
잡기 열세에서 굳힌 상대에게 엉성한 기술을 거는 것만으로 되치기가 난다.
ⓐ/ⓒ 논의의 틀이 여기서 바뀐다.

## 4. 함께 보이는 것 (판단 아님, 관찰)

- **수비자세 −2 가 되치기의 주 동력이다.** 읽기 없이 나는 되치기 3개도, 읽기 없이 나는
  근접 실패 6개 중 5개도 수비자세 −2 를 포함한다. §4 에서 이 항은 "굳힌 상대에겐
  점수가 안 난다"를 표현하려고 넣은 것인데, 같은 부호가 공격자를 되치기 구간으로도
  밀어넣는다. **웅크리고만 있던 상대에게 되치기를 당하는 그림**이 규칙상 성립한다.
- 되치기 31조합 중 **체력 항이 0 인 것이 19개**다. 되치기는 상대가 지쳐서 나는 게 아니다.
- 한판(32조합)과 되치기(31조합)의 수가 거의 같다. 판정식이 양극단에 대칭적이다.
