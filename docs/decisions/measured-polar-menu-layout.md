# 기술 결정: 방사형 메뉴를 고정 각도표에서 실측 기반 배치 알고리즘으로 교체

작성 2026-08-14 · 상태: 구현·검증 완료

## Problem — 문제

`LiveMatchPanel`의 모든 축 선택(손/코어/하체/기술/회피 존)은 반지름 R,
−90°~+90° 균등분배 공식(`angleDeg = -90 + idx*(180/(n-1))`)으로 옵션 버튼을
배치했다. 이 공식은 항목 개수만 보고 각 라벨의 실제 텍스트 길이를 전혀
보지 않는다.

손 축 스테이지1(왼손/오른손/회피 3항목)에 한해서는 균등분배 대신 A 캐릭터
반대편 안전 반원(cosθ≤0)에 배치하는 별도 고정 각도표를 썼는데, 이마저도
Play 실측에서 왼손·회피 라벨이 각 38.6px씩 화면 밖으로 잘리는 게 확인됐다.
반지름·각도를 손으로 재조정(40, 95°/180°/265°)해 회피 하나만 22px 클립을
"딤 처리 전례보다 작은 손실"이라는 근거로 받아들였는데, 이 판단이 실제
스크린샷에서는 "체감상 불가"로 뒤집혔다. 같은 시점에 항목이 가장 많은
기술 휠(8항목)에서도 하단 라벨끼리 겹치고, 좌상단 항목이 화면 밖으로
잘리고, 세로 구간에 라벨이 뭉치는 문제가 새로 신고됐다.

두 증상의 뿌리는 하나였다: **배치식이 라벨 폭을 모른다.** 짧은 라벨("왼손")
옆에는 빈 공간이 남고, 긴 라벨("모두걸기")은 이웃과 겹친다. 반지름을 키우면
겹침은 줄지만 그만큼 화면 밖으로 밀려나는 항목이 늘어난다 — 손으로 값 하나를
고쳐서 해결되는 문제가 아니라, 두 제약(겹침 없음 / 화면 안에 있음)이
구조적으로 상충한다.

## Action — 한 일

고정값 튜닝을 그만두고 실측 기반 배치 알고리즘을 새로 짰다:

1. **`MeasureLabelWidth`** — 화면 밖 스크래치 `TextMeshProUGUI`에 실제 라벨
   문자열을 넣고 `GetPreferredValues()`로 진짜 렌더 폭을 잰다. 짐작이 아니라
   TMP 자신에게 묻는다.
2. **`TryPackAngles`** — 각 라벨 폭을 반지름에서의 반각(atan2 기반)으로
   환산해, 이웃 항목과 겹치지 않도록 `PolarGapDeg=4f` 여유를 두고 아크에
   순서대로 채운다. 항목 수가 몇 개든 같은 함수가 동작한다 — 손 축 전용
   고정 각도표는 이제 존재하지 않는다.
3. **`AllWithinSafeArea`** — 배치 결과 전부가 하드코딩된 참조 해상도
   세이프 박스(`1920×1080`, 여백 10px) 안에 있는지 검사.
4. **`SolvePolarLayout`** — 반지름을 키워 각도 겹침을 풀면 화면 밖으로
   밀려나는 상충을 명시적 우선순위로 해소: **화면 안전 > 겹침 없음 >
   가독성(넓은 라벨)** 순으로, 라벨 폭 상한(`PolarMinWidth=56f`~
   `PolarMaxWidth=150f`)을 좁혀가며 재시도한다.

손 축 스테이지1도 이 일반 함수(`RebuildAxisOptions<T>`)에 `arcStartDeg:
90f` 인자 하나로 흡수시켰다 — 예전에 있던 `RebuildHandTopStage`/
`HandTopSlots`/`HandTopRadius` 전용 코드는 전부 삭제했다. 이제 "항목이
3개인 축"과 "항목이 8개인 축"이 코드 경로를 공유한다.

## Result — 결과

프로그램적 쌍별 겹침 검사(`Rect.Overlaps`)와 화면 경계 검사를, 앱에 실재하는
7개 스테이지(손 스테이지1/2, 회피 존 좌/우, 코어, 하체, 최대 항목 수인 기술
휠 8개)에 전부 돌려 **겹침 0 · 화면 이탈 0**을 확인했다. 손 스테이지1의
"회피" 라벨은 xMin=10.00으로 정확히 세이프 마진 경계에 붙어 잘림이 완전히
사라졌다(이전엔 −22px, 화면 밖).

부수 효과: 뜯기(2차 예약 항목) 같은 향후 항목 추가나 라벨 문구 변경이
생겨도 이 알고리즘은 재작업 없이 자동으로 대응한다 — 고정 각도표 시절에는
항목이 하나 늘 때마다 다시 실측하고 다시 조정해야 했다.

## 면접 예상 질문

**Q. 왜 반지름을 키우는 것보다 "라벨 폭 상한을 좁힌다"는 선택을 우선했나?**
반지름 확대는 각도 겹침에는 약이지만 화면 이탈에는 독이다 — 두 증상이
반대 방향으로 반응해서 한 손잡이로 동시에 풀 수 없다. 화면 밖으로
잘리는 라벨은 사용자에게 완전히 안 보이는 반면, 약간 좁아진 라벨은
여전히 읽히고 기능한다. 그래서 "화면 안전"을 최우선 제약으로 고정하고,
그 안에서 겹침을 없애는 여유를 라벨 폭 쪽에서 확보하도록 순서를 정했다.

**Q. 처음부터 이 알고리즘으로 만들지 않고 왜 고정값 조정을 먼저 시도했나?**
손 스테이지1은 항목이 3개로 고정돼 있고 안전 아크라는 특수 제약이 있어서,
처음엔 국소적인 문제로 보고 고정 각도표로 빠르게 풀었다. 그런데 같은
근본 원인(라벨 폭 무시)이 항목 수가 많은 기술 휠에서 다른 증상(겹침)으로
다시 나타나면서, 두 증상이 사실 하나의 구조적 결함이라는 게 드러났다 —
그 시점에 국소 수정을 버리고 일반 알고리즘으로 통합했다.

## 말할 가치가 있는 지점

- 사용자가 이전에 수용했던 타협(22px 클립)을 실측 스크린샷 하나로
  명시적으로 철회했을 때, "이미 승인받은 값이니 유지"가 아니라 실제
  체감이 기준이라는 걸 받아들이고 재설계했다.
- 국소 증상 두 개(스테이지1 클립, 기술 휠 겹침)를 각각 패치하는 대신
  공통 원인(라벨 폭을 안 보는 배치식)을 찾아 하나의 알고리즘으로 통합해,
  향후 항목 수·라벨 문구가 바뀌어도 재작업이 필요 없는 구조로 만들었다.
- "화면 밖 스크래치 텍스트로 실제 폭을 잰다"는 방법 자체가, 폰트·패딩·
  자동 크기 조정이 얽힌 상황에서 계산으로 추정하는 대신 엔진(TMP)에게
  직접 묻는 편이 더 정확하고 유지보수가 쉽다는 판단에서 나왔다.
