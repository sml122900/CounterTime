# 기술 결정: 동작 보존 리팩터링을 "지문 diff" 로 강제

작성 2026-08-10 · 상태: **적용 완료, 1~3단계 26커밋 내내 사용**

## Problem — 문제

시나리오가 공급하던 `ReadLevel` 을 알고리즘이 공급하도록 바꾸는 작업이었다. 요구가 명확했다.

> 대조 모드(스크립트 경로)를 지우거나 대체하지 않는다. 인터페이스 뒤로 옮기기만 한다.
> **동작이 1비트라도 바뀌면 잘못한 것이다.**

대조 모드는 이 저장소의 회귀 기준선이다. 42노드 참조 경기와 130개 테스트가 그 위에 서 있다. 그런데 이번 작업은 **그 경로에 무엇이 값을 공급하는지를 통째로 갈아끼우는** 것이라, 경계가 새면 기준선 자체가 조용히 오염된다.

### 테스트만으로는 부족한 이유

"테스트 130개 초록"은 **테스트가 보는 것**만 지킨다. 이번에 건드리는 것은 러너의 실행 순서, 커밋이 만들어지는 지점, 읽기 값이 주입되는 지점이었다 — 어느 것도 단위 테스트가 직접 단언하지 않는다.

구체적으로, 다음은 전부 130개를 초록으로 둔 채 통과할 수 있는 변경이다.

- 교환 조립 순서가 바뀌어 잡기 이벤트가 한 프레임 늦게 나감
- 자세 유지 규칙이 미묘하게 달라져 3번째 교환부터 수비자세 항이 −2 대신 0
- 시계가 교환당 5초 대신 3초를 태움 (그리고 경기가 나중에 다르게 끝남)

셋 다 **에러가 안 나면서 틀리는** 부류다. 이 저장소가 이미 여러 번 데인 바로 그 종류다.

## Action — 한 일

### 지문의 대상을 "이벤트 + 상태 전량" 으로 잡았다

`MatchRunner.Mainline` 17노드를 걷게 하고, 노드마다 다음을 텍스트로 찍었다.

- 그 노드가 낸 **모든 `MatchEvent`** — 판정(합·등급·득점자·되치기·5항 전부), 잡기 변화, 뜯기, 카운터 준비, 지도, 심판 tell, 그쳐, 종료
- 그 노드 직후의 **엔진 전체 상태** — 양쪽 잡기·체력·지도, 시계, 종료 여부

52행이 나온다. 단계마다 이걸 뜨고 이전 단계와 `diff` 했다.

```
=== step2.5 vs step3.2 (must be empty) ===
IDENTICAL — 0 lines differ
```

**요약값이 아니라 전량을 찍은 것**이 핵심이다. "최종 승자가 같다" 는 세 종류의 오류를 다 통과시킨다.

### 프로덕션 코드를 그대로 돌렸다 — 재구현하지 않았다

`MatchRunner` 는 `MonoBehaviour` 라 헤드리스로 못 돈다. 러너 로직을 테스트에 복제하면 **복제본을 검증하는** 셈이라 의미가 없다.

대신 스크래치패드 하니스에 UnityEngine 셰임 60줄을 넣었다.

```csharp
namespace UnityEngine
{
    public class MonoBehaviour : Object { }
    public sealed class TextAsset : Object { public string text { get; } }
    public static class Mathf  { public static int Clamp(...) }
    public static class JsonUtility { public static T FromJson<T>(string json) }
    // Debug, SerializeField, Input, KeyCode …
}
```

셰임은 **배관만** 공급한다 — 로깅, 클램프, JSON, 기반 클래스. 규칙은 한 줄도 재구현하지 않았다. 그래서 `MatchRunner.cs`·`ScriptedAssembler.cs`·`ScenarioTurnChoices.cs` 를 **저장소의 파일 그대로** 컴파일해 굴린다.

### 수정 전/후를 둘 다 돌려서 비교했다

`git stash` 로 대상 파일만 되돌리고 하니스를 한 번 더 돌려 지문을 뜬 뒤, 두 지문을 diff 했다. 0.5단계(`default(TurnChoice)` 제거)에서는 이 방식으로 **85개 노드 전량**을 통과시켜 다음을 분리해 보였다.

| 비교 대상 | 결과 |
|---|---|
| 파싱 성공 48행 (who/hand/core/legs/ownHand 전부) | 완전 동일 |
| 노드별 성공/실패 판정 85행 | 완전 동일 |
| 파싱 **거부** 37행의 out 값 | `Aggressive/Attack` → `Neutral/Neutral` |

바뀐 것이 정확히 어디인지, 그리고 그 자리를 아무도 읽지 않는다는 것(호출부 2곳 모두 bool 로 가드)을 같이 보였다.

## Result — 결과

### 26커밋 내내 IDENTICAL

asmdef 신설, 인터페이스 3종 추출, 클래스 개명, 러너 배선 변경, **그리고 Core 규칙 변경(v3.4)** 까지 건너면서 지문이 한 번도 안 바뀌었다.

마지막 것이 특히 중요하다. v3.4(득점 후 그쳐)는 `MatchEngine.ResolveExchange` 를 고치는 변경인데도 지문이 그대로였다 — **메인라인의 판정이 노포인트 3건과 경기 종료 한판뿐이라 새 규칙의 두 예외에 정확히 걸린다.** 규칙을 그렇게 쓴 것이 맞았는지가 지문으로 즉시 확인됐다.

### 실제로 잡은 것

- **1단계**: `MatchRunner` 에 `using CounterTime.Brain;` 누락 → 하니스 컴파일 에러. Unity 를 켜기 전에 잡혔다
- **0.5단계**: 거부 경로의 out 값이 37개 노드에서 `Aggressive/Attack` 이라는 것을 전수로 확인. 그 불변식을 커밋되는 테스트로 옮겼다
- **3.10단계**: Core 규칙 변경 후 기존 테스트 하나의 기대값이 움직인 것을 즉시 식별. 지문이 아니라 테스트가 잡았지만, 지문이 동시에 IDENTICAL 이었기에 **"규칙 변경의 정당한 귀결"과 "리팩터링 사고"를 즉시 구분**할 수 있었다

### 부수 효과 — Core 순수성이 컴파일 조건으로 남았다

셰임에 없는 UnityEngine 타입을 Core 나 Brain 이 쓰기 시작하면 하니스가 즉시 깨진다. `CounterTime.Brain` 의 `UnityEngine` 참조 0 은 grep 이 아니라 **로드된 어셈블리의 참조 목록**으로 확인했다.

```
CounterTime.Brain referenced assemblies: netstandard, CounterTime.Core
```

## 면접 예상 질문

**"테스트가 있는데 지문이 왜 또 필요한가?"**
테스트는 **의도한 것**을 지키고 지문은 **의도하지 않은 것**을 잡는다. 이번 작업은 러너의 실행 순서와 값 주입 지점을 바꾸는 일이었고, 그건 어느 단위 테스트도 직접 단언하지 않는다. 실제로 130개를 초록으로 둔 채 통과할 수 있는 회귀 세 가지를 미리 열거해뒀다.

**"셰임으로 돌린 게 진짜 검증인가?"**
셰임이 무엇을 공급하는지가 답을 가른다. 규칙을 셰임했으면 검증이 아니다 — 이건 로깅·클램프·JSON·기반 클래스만 공급하고, 검증 대상 코드는 저장소 파일 그대로다. 그리고 셰임이 못 덮는 영역(`GameObject`/`AddComponent` 를 쓰는 러너 테스트 3개)은 **하니스가 스스로 범위를 밝히게** 해뒀다.

```
COVERAGE: CounterTime.Core.Tests + CounterTime.Brain.Tests + the MonoBehaviour-free
          files of CounterTime.Game.Tests. MatchRunnerHandActionTests (3) is NOT run
          here — it needs GameObject/TextAsset, i.e. the Unity Test Runner.
```

**"지문이 바뀌면 어떻게 하나?"**
바뀌는 것 자체는 실패가 아니다 — 규칙을 고치면 바뀌어야 정상이다. 절차를 그렇게 정해뒀다: 바뀌면 **무엇이 어떻게 바뀌었는지 보고하고, 메인라인의 최종 판정(m36 sum 7 / 한판 / winner=A)만 별도로 확인**한다. 그 둘이 깨지면 멈춘다.

## 말할 가치가 있는 지점

이 방식의 진짜 비용은 **지문 자체가 회귀 대상이 된다**는 것이다. 계측 코드를 추가한 회차에 지문 형식이 바뀌어 diff 가 거짓 양성을 냈다 — 어셈블러 계수 3행을 넣은 직후였다. 기준선을 "같은 계측이 들어간 실행"으로 다시 떠서 비교해야 했다.

그래서 지문에 넣을 것과 안 넣을 것을 나눴다: **엔진이 낸 것만 지문에 들어가고, 내가 궁금해서 찍는 값(습관 발화 횟수, 사다리 행별 적중, 체력 궤적)은 지문 범위 밖에 출력**한다. 계측을 늘려도 기준선이 안 흔들린다.
