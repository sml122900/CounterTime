# 기술 결정: 뜯긴 존 재잡기 쿨다운을 "검사-후-감소" 순서의 존별 카운터로 모델링했다

작성 2026-08-19 · 상태: **적용 완료**

## Problem — 문제

사용자가 확정한 규칙은 "뜯기 성공으로 해제된 존은 그 교환 + 다음 1교환
동안 재잡기 불가, 매트릭스보다 우선"이었다. 규칙 자체(무엇을 막을지)는
명확했지만 구현 방식(카운터를 언제 얼마로 세팅하고 언제 감소시키는가)은
지정돼 있지 않았다.

`MatchEngine.ResolveGripExchangeRevised`는 이미 정해진 순서로 돈다 — 뜯기
같은 논-매트릭스 손 액션(`ResolveNonMatrixHandAction`)이 먼저 처리되고,
그 직후 같은 호출 안에서 양쪽의 그랩 시도가 매트릭스로 들어간다. 뜯기가
이 순서의 앞쪽에서 일어나므로, "그 교환"과 "다음 교환"을 구분하는 카운터를
순진하게 만들면 둘 중 하나만 막을 위험이 있었다 — 카운터를 쿨다운 값
그대로(`TearRegripCooldown`=1) 세팅하고 매 교환 끝에 그냥 1씩 깎으면, 뜯긴
바로 그 교환이 끝나는 순간 카운터가 이미 0이 돼 **다음** 교환은 못 막는다.

## Action — 한 것

카운터를 "쿨다운 값"이 아니라 "이번 검사 시점을 포함해 몇 번 더 검사를
막아야 하는가"로 재정의했다. 뜯기 성공 시 `1 + TearRegripCooldown`(기본
1+1=2)으로 세팅하고, 매 `ResolveGripExchangeRevised` 호출 끝에서 정확히
1씩 줄인다(0에서 바닥). 매트릭스가 그랩 성공 여부를 계산하는 지점은
**감소보다 항상 먼저**이므로, 뜯기가 일어난 바로 그 호출에서도 카운터가
아직 2인 채로 검사된다.

시퀀스를 코드를 짜기 전에 손으로 검산했다:

```
교환 N   : 뜯기 성공 → 카운터 세팅(2) → 이 교환 매트릭스 검사(2>0, 차단) → 교환 끝 감소(2→1)
교환 N+1 : 매트릭스 검사(1>0, 차단) → 감소(1→0)
교환 N+2 : 매트릭스 검사(0, 통과) → 재잡기 성립
```

정확히 "그 교환 + 다음 1교환" 두 번을 차단하고 세 번째부터 풀린다 — 규칙
문구를 그대로 만족한다.

키는 (victim `FighterId`, `DefenseZone`) 쌍으로 뒀다. 새 매핑을 만들지
않고 기존 `ZoneOf(HandTarget)`을 그대로 재사용했다 — 뜯기가 "내 부위 중
잡힌 곳"(`TearZone`)을 가리키는 신원과, 매트릭스의 방어 존 체크
(`IsZoneDefended`)가 "그 존을 방어하는 쪽"을 가리키는 신원이 이미 같은
값이기 때문이다. 손을 바꿔 재시도해도(예: 오른소매를 다른 손으로) 막힌
것은 존 자체라 자연히 우회가 안 된다.

## Result — 결과

`GripTearRegripCooldownTests`에 커버 테스트 2개를 추가해 "그 교환 실패 →
다음 교환도 실패 → 그다음 교환부터 성공" 시퀀스와 "무관한 존은 안 막힌다"를
직접 고정했다. "오른소매 비견고 + 팔꿈치로 뜯기 3연속" 시나리오를 이벤트
로그로 재현해(뜯기 1회 성공 → 재확보 2교환 연속 실패 → 3번째 교환에서
성공) 설계한 시퀀스가 실제로 그대로 나오는 것을 확인했다. 하니스
327/327, 42노드 지문 IDENTICAL.

## 면접 예상 질문

**"카운터를 `TearRegripCooldown` 그대로 두고 매트릭스 체크를 감소 뒤에
놓으면 안 됐나?"**
같은 결과를 낼 수는 있지만, 그러면 뜯기와 매트릭스가 "이번 교환 안에서
어느 쪽이 먼저 도는가"라는 호출 순서 자체에 결과가 더 민감해진다. 지금
방식은 "검사는 항상 감소보다 먼저"라는 불변식 하나만 지키면 되고, 그
불변식은 기존 교차잡기 롤링 타이머(`TickCrossGripTimer`)가 이미 서 있는
바로 그 자리(매트릭스 뒤)에 한 줄을 더하는 것으로 자동 성립했다 — 새
생명주기를 만들지 않고 기존 타이머와 같은 자리를 탔다.

## 말할 가치가 있는 지점

규칙 자체("그 교환 + 다음 1교환")는 사용자가 자연어로 확정해 줬지만, 그
자연어를 "카운터 초기값과 감소 시점을 어떻게 짜야 정확히 그 길이가
나오는가"라는 이산 시퀀스 문제로 옮기는 건 구현자의 몫이었다. 첫 직관
("카운터 = 쿨다운 값 그대로")은 표로 검산해보니 한 교환이 모자랐다 —
오프바이원을 코드로 겪고 테스트가 실패한 뒤 고치는 대신, 코드를 짜기
전에 시퀀스를 표로 먼저 펼쳐 잡은 경우다.
