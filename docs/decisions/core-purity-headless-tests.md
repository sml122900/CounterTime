# 기술 결정: Core 순수성을 테스트 실행 경로로 쓴다

작성 2026-08-09 · 상태: **적용 완료 (개발 루프 한정)**

## Problem — 문제

매치 엔진을 7단계로 나눠 구현하기로 했고, 각 단계는 "테스트 통과"로 완료를 정의했다. 106개 테스트를 단계마다 돌려야 한다는 뜻이다.

이 프로젝트의 개발 루프는 Unity MCP 다. 스크립트를 고치고 MCP 로 콘솔을 읽어 컴파일 에러를 확인한다. 그런데 **MCP 로는 EditMode 테스트를 못 돌린다.**

```
UNEXPECTED_ERROR: User interactions are not supported for MCP tool calls.
```

`TestRunnerApi.Execute` 가 막혀 있다. 우회 시도도 막혔다 — 콜백 클래스를 중첩으로 쓰면 샌드박스의 코드 정규화기가 클래스를 바깥으로 끌어내 상수 참조가 깨진다.

남은 선택지는 이랬다.

| 선택지 | 문제 |
|---|---|
| 사람이 매 단계 Test Runner 를 눌러준다 | 단계마다 사람을 기다린다. 7단계 × 여러 회 |
| 컴파일만 확인하고 테스트는 마지막에 | 단계별 완료 판정이 무너진다. 6단계에서 깨진 걸 7단계에서 찾게 된다 |
| Unity 배치 모드(`-runTests`) | 에디터가 이미 프로젝트를 잠그고 있다. 두 번째 인스턴스가 같은 프로젝트를 못 연다 |

## Action — 한 것

### 이 프로젝트에는 이미 답이 있었다

`CLAUDE.md` 의 제1 규칙이다.

> `CounterTime.Core` — **순수 C#. UnityEngine 참조 금지.** MonoBehaviour 없음. **Unity 없이도 콘솔/테스트로 굴러가야 한다.**

이 규칙은 아키텍처 위생을 위해 쓰인 것이었다. 그런데 그대로 읽으면 **실행 경로**이기도 하다. Core 가 진짜로 순수하다면 Unity 밖에서 컴파일되고 실행된다.

확인해 보니 도구가 다 있었다.

- `dotnet` SDK 10.0.302
- `nunit.framework.dll` — `Library/PackageCache/com.unity.ext.nunit@…/net40/unity-custom/`

스크래치패드에 콘솔 프로젝트를 만들고 **커밋된 NUnit 테스트 파일을 그대로** 컴파일했다. 테스트를 다시 쓰지 않았다는 점이 중요하다 — 검증 대상이 저장소에 들어가는 산출물 그 자체여야 한다.

```xml
<Compile Include="Program.cs" />
<Compile Include="…\Assets\_Project\Scripts\Core\**\*.cs" />
<Reference Include="nunit.framework">
  <HintPath>…\net40\unity-custom\nunit.framework.dll</HintPath>
</Reference>
```

`Program.cs` 는 40줄짜리 리플렉션 러너다. `TestAttribute` 가 붙은 메서드를 찾아 `SetUp` 을 돌리고 호출한다. NUnit 콘솔 러너를 NuGet 에서 받지 않은 이유는 네트워크 의존을 안 만들기 위해서다.

```
passed=106 failed=0
```

### 하니스는 저장소에 넣지 않았다

스크래치패드에만 둔다. 커밋되는 산출물은 **NUnit 테스트 파일 쪽**이고, 그것은 Unity Test Runner 에서 정상적으로 돈다. 하니스는 내 개발 루프의 도구지 프로젝트의 일부가 아니다.

사람이 확인할 때는 여전히 `Window > General > Test Runner > EditMode > Run All` 이다. 두 경로가 같은 파일을 실행하므로 결과가 갈릴 일이 없다.

### 부수 효과 — 순수성이 실제로 검증된다

이 방식은 Core 에 `using UnityEngine;` 이 하나라도 들어가면 **즉시 컴파일 실패한다.** 규칙이 주석에 적힌 다짐이 아니라 빌드 조건이 된다.

세션 끝에 확인했다.

```
Select-String -Path "…\Scripts\Core\*.cs" -Pattern "UnityEngine" | Measure → 0
```

### 검토했다가 안 택한 것

- **테스트를 콘솔용으로 따로 쓴다** — 두 벌이 되면 갈라진다. 커밋된 것과 실행되는 것이 달라지는 순간 이 방식의 의미가 없다
- **Core 에서 NUnit 을 걷어내고 자체 assert 를 쓴다** — Unity Test Runner 통합을 잃는다. 사람이 눌러 볼 경로가 사라지면 안 된다
- **MCP 우회를 더 파고든다** — 콜백 등록 방식을 몇 번 바꿔봤지만 샌드박스 정규화기와 계속 부딪혔다. 시간 대비 이득이 없고, 성공해도 Unity 에디터 상태에 의존하는 취약한 경로가 된다

## Result — 결과

- 7단계 전부 단계 끝에서 전체 테스트를 돌리고 넘어갔다. 106개까지 누적하는 동안 회귀 0
- 실제로 한 번 잡았다 — 6단계 리플레이 테스트에서 A 체력이 90 예상인데 93 이 나왔다. 지도 → 그쳐 → §5.3 매트 회복 +3 이 같은 교환 안에서 일어난 것. 문서(m15 스냅샷)와 규칙(§5.3)이 어긋난 지점이라 양쪽 다 테스트로 고정했다
- Core 의 UnityEngine 참조 **0** 을 빌드 조건으로 강제

### 한계

- Unity 직렬화·Humanoid 리타게팅처럼 **엔진이 있어야 성립하는 것은 이 경로로 검증 못 한다.** Core 에 그런 게 없어야 정상이므로, 이 경로가 막히면 그 자체가 설계가 샜다는 신호다
- `.csproj` 가 절대 경로를 쓴다. 다른 PC 로 옮기면 다시 만들어야 한다 — 어차피 커밋 안 하는 임시 도구라 감수했다

## 이력서 한 줄

> 엔진 통합 테스트 러너가 자동화 채널에서 차단된 상황에서, 아키텍처 규칙으로만 존재하던 "코어는 엔진 비의존" 조건을 실제 실행 경로로 전환해 커밋된 테스트 파일을 수정 없이 엔진 밖에서 구동했습니다. 그 결과 7단계 구현 내내 매 단계 106개 테스트를 사람 개입 없이 돌렸고, 동시에 코어 순수성이 주석이 아니라 컴파일 조건으로 강제되게 했습니다.
