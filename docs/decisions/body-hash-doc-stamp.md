# 기술 결정: 문서 스탬프를 커밋 해시가 아니라 본문 해시로

작성 2026-08-09 · 상태: **적용 완료, 훅으로 자동 유지**

## Problem — 문제

`MATCH_RULES.md` 는 이 프로젝트의 단일 출처다. `CounterTime.Core` 가 이 문서를 구현하고, 코드와 문서가 어긋나면 **문서가 이긴다**고 문서 스스로 선언한다.

그런데 이 문서는 자주 대화창에 붙여넣어진다. 패치 지시도, 규칙 확인도 사본을 통해 오간다. 그래서 요구가 나왔다.

> 문서에 `<!-- v3.1 | 33ecd10 -->` 헤더를 넣고, 그 파일을 편집하는 커밋과 **같은 커밋에서** 갱신할 것.

목적은 분명했다 — 손에 든 사본이 저장소의 그것과 같은지 확인하는 것. 문제는 **커밋 해시로는 그게 안 된다**는 점이었다.

### 자기참조라서 수렴하지 않는다

커밋 해시는 그 커밋의 내용에서 나온다. 해시를 파일에 쓰면 파일 내용이 바뀌고, 내용이 바뀌면 해시가 바뀐다. 쓰려는 값이 쓰는 행위 때문에 무효가 된다.

```
편집 → 커밋 abc123 생성 → abc123 을 파일에 씀 → 내용 변경 → 이제 해시는 def456
```

`--amend` 로 다시 써도 같다. 절대 수렴하지 않는다.

실제로 첫 시도(`dc23109`)에서 곧바로 드러났다. 스탬프는 `33ecd10` 인데 그 파일을 실제로 마지막에 고친 커밋은 `dc23109` 다 — 만들자마자 한 커밋 뒤처진 상태였다.

### 더 나쁜 것: 잡아야 할 실패를 못 잡는다

스탬프의 목적은 "이 사본이 진짜인가"다. 그런데 커밋 해시는 **커밋된 것에 대해서만** 말한다. 누가 워킹 트리에서 문서를 고치고 커밋하지 않은 채 그 상태를 붙여넣으면, 스탬프는 여전히 이전 커밋을 가리키며 아무 이상이 없다고 말한다.

**존재 이유였던 실패를 정확히 못 잡는 장치**였다.

## Action — 한 것

### 1. 해시 대상을 커밋이 아니라 본문으로

```
<!-- v3.2 | body:e11de04 -->
```

`body:` 뒤는 **1행을 제외한 파일 본문**의 `git hash-object`(CR 제거 후).

핵심은 이것이다 — **스탬프를 쓰는 행위가 스탬프가 재는 대상을 바꾸지 않는다.** 1행은 해시 계산에서 빠지므로, 1행에 무엇을 쓰든 본문 해시는 그대로다. 첫 시도에 수렴하고 사람의 판단이 개입할 여지가 없다.

| | 커밋 해시 | 본문 해시 |
|---|---|---|
| 수렴 | 안 됨 (자기참조) | 1회 |
| 미커밋 편집 감지 | **못 함** | 함 |
| 사본만 보고 검증 | 저장소 접근 필요 | **파일 하나면 됨** |
| 사람의 판단 | 필요 (어느 커밋을 쓸지) | 없음 |

세 번째 줄이 실질적인 이득이다. 대화창에 붙은 문서 하나만 있으면 1행을 떼고 나머지를 해싱해 1행과 대조하면 된다. 안 맞으면 그 사본은 훅 없이 편집됐거나 손으로 고쳐진 것이고, **그쪽에 맞추면 안 된다.**

### 2. 유지를 사람에게 맡기지 않았다

규칙은 "편집과 같은 커밋에서 갱신"이다. 사람이 기억해야 하면 언젠가 잊는다. `tools/githooks/pre-commit` 이 스테이징된 문서의 스탬프를 다시 쓰고 재스테이징한다.

**실패시키지 않고 자동 수정하게 했다.** 스탬프에는 사람의 판단이 0이므로, 커밋을 막아봐야 "고치고 다시 커밋"이라는 왕복만 늘어난다.

훅을 저장소에 넣은 이유는 새 클론에서도 돌게 하기 위해서다. 그래서 `.gitattributes` 에 `*.sh` 와 `tools/githooks/*` 를 `eol=lf` 로 고정했다 — **안 하면 새 Windows 클론이 CRLF 로 받아 셔뱅이 깨지고, 훅을 커밋한 이유가 통째로 무너진다.**

### 3. 훅이 대상을 스스로 찾게 했다 (두 번 고쳐서)

처음에는 훅에 파일 목록을 하드코딩했다. 두 번 무음 실패했다 — 상세는 `docs/troubleshooting/git-hook-silent-skip.md`.

최종형은 경로를 모른다. **1행이 스탬프 형식인 staged `*.md` 를 전부** 대상으로 삼는다.

```sh
git -c core.quotePath=false diff --cached --name-only --diff-filter=ACM -- '*.md' \
  | while IFS= read -r f; do
  [ -f "$f" ] || continue
  head -n 1 "$f" | tr -d '\r' \
    | grep -qE '^<!-- v[^ ]+ \| body:[0-9a-f]{7} -->$' || continue
  sh tools/stamp.sh "$f"
  git add "$f"
done
```

부수 효과가 좋다. **플레이스홀더 스탬프를 붙이는 행위가 곧 등록**이고, 1행을 지우면 등록이 해제된다. 문서를 옮겨도 안 깨진다.

### 검토했다가 안 택한 것

- **커밋 후 별도 커밋으로 스탬프 갱신** — 매 문서 수정이 커밋 2개가 된다. 그리고 두 커밋 사이에는 스탬프가 틀린 상태가 저장소에 남는다
- **버전 문자열만 두고 해시 생략** — `v3.2` 만으로는 같은 버전 안에서의 편집을 구분 못 한다. 오늘 v3.1 문서를 세 번 고쳤는데 전부 같은 버전이었다
- **`-z` + `read -d ''` 로 비ASCII 경로 처리** — `read -d ''` 는 bash 확장이다. 셔뱅이 `#!/bin/sh` 인데 Git Bash 에서만 우연히 돌고 `/bin/sh` 가 dash 인 환경에서 조용히 깨진다. **지금 고치려는 실패와 같은 종류로 바뀌므로 이득이 없다.** `-c core.quotePath=false` 한 토큰으로 해결
- **`--check` 를 엄격하게 유지** — 스탬프 없는 파일에 exit 2 를 내면 `--check md/*.md` 가 정상 저장소에서 실패한다(`md/STATUS.md` 는 스탬프가 없다). **아무 문제 없을 때 에러를 내는 점검은 사람이 무시하는 법을 배운다.** `--check` 에서는 미등록 파일을 건너뛰게 바꿨다 — 훅과 같은 규칙(1행이 소속을 정한다)

## Result — 결과

- 두 문서(`md/MATCH_RULES.md`, `md/CORE_DESIGN_MatchEngine.md`)가 본문 스탬프를 달고 훅으로 자동 유지된다
- 첫 실행에 수렴하고 재실행은 `already current` — 멱등
- `--check` 는 실제 stale 을 잡고(exit 1) 정상 저장소에서는 exit 0
- 훅을 실제 커밋으로 관통 검증: `a24d23c` → `c9290de` 로 커밋 안에서 다시 써졌다

### 실패 모드가 안전한 쪽이다

`core.hooksPath` 는 클론마다 수동 설정이고 자동화할 수 없다. 하지만 훅이 안 돌면 스탬프는 **틀린 값이 되는 게 아니라 낡은 값이 된다.** 그리고 낡은 스탬프는 문서를 읽는 시점에 본문을 다시 해싱하면 드러난다.

침묵하는 오류가 아니라 **사용 시점에 드러나는 지연**이다. 그래서 대응은 "세션 시작 시 `git config core.hooksPath` 확인" 한 줄로 충분하고, `CLAUDE.md` 의 `## Fresh clone` 에 넣었다. CLAUDE.md 는 매 세션 로드되므로 잊어도 다음 세션 첫머리에 걸린다.

### 규칙을 어디에 두는가

이 결정에는 부가 교훈이 하나 붙었다. 스탬프 컨벤션을 처음에 **어시스턴트 세션 메모리**에만 저장했다가 사람에게 지적받았다.

> 세션 메모리에만 있는 규칙은 규칙이 아니다 — diff 에도, 다른 도구에도, 다음 세션에도 안 보인다.

메모리 항목을 지우고 `CLAUDE.md` 로 옮겼다. 저장소 안에 있어야 diff 로 보이고 사람이 검토할 수 있다.

## 이력서 한 줄

> 문서 무결성 스탬프를 커밋 해시에서 본문 해시로 재설계해, 해시를 기록하는 행위가 해시 대상을 변경하는 자기참조 문제를 제거하고 미커밋 편집까지 탐지 범위에 넣었습니다. 유지는 저장소에 커밋한 pre-commit 훅에 위임하되 훅이 경로 목록 대신 파일 1행으로 대상을 스스로 판별하게 해, 문서 위치가 바뀌어도 검증이 조용히 중단되지 않도록 했습니다.
