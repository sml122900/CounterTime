## §2 — 승률 붕괴 원인 분리 (B 의 그립 수정 vs AutoA 의 휴리스틱 개편)

3콤보 모두 확보했다 — 4번째("new AutoA × old B")는 실제로 존재한 적 없는
조합이라 아래 사유로 구성하지 않았다(작업 지시가 명시적으로 허용한 경로).

**N 을 낮추지 않았다**: §1/§3(6×500=3000경기, 0.2초 실측)와 콤보2(6×500=3000경기,
+대진표 500회)를 포함해 이 문서의 모든 실행은 기존 문서들과 같은 N=500 을
그대로 썼다 — 헤드리스 하니스가 워낙 빨라서(3000경기가 1초 미만) 낮출 필요가
없었다. 낮춘 항목은 없다.

**측정 방법**: 콤보1/콤보3은 이미 실행·발행된 문서 수치를 그대로 재사용
(재실행 없음 — 지시 그대로 "메트릭이 맞으면 재사용"). 콤보2는 이번 세션이
`git worktree add <scratch>/wt-611e1e2 611e1e2`로 커밋 611e1e2 를 읽기 전용
체크아웃한 뒤, 그 커밋에 이미 있던(이번 세션이 한 글자도 안 고친) `dotnet run
-- --overnight` 를 워크트리 안에서 그대로 실행해 확보했다 — nunit.framework.dll
빌드 종속성(Library/PackageCache, git 미추적 산출물)만 메인 트리에서 복사해
넣었다(git 추적 파일은 전혀 건드리지 않음). 실행 후 `git worktree remove` 로
정리 완료.

### 이 데이터가 가리키는 것 (수치 비교, 튜닝 판단 아님)

**콤보1→콤보2 (B 그립 수정만 적용, AutoA 는 그대로)**: 6상대 평균 승률이

새로 생겼다 — B 가 양손을 다 쥘 수 있게 되자 AutoA 의 옛 그립다지기 종료조건
(`ownGrip<1`)이 파리티에서 못 빠져나오는 새 교착이 실제로 재현된다(이건 이

현상의 재수집 시도 초기 버전이라, 그 서술과 정성적으로 일치한다).

**콤보2→콤보3 (그 위에 AutoA 3중 안전장치까지 적용)**: 6상대 평균 승률이
77.7%→4.3%로 추가로 **73.4%p** 더 떨어진다 — 콤보1→콤보2 낙폭(21.4%p)의
약 3.4배. 동시에 평균 교환수는 620.8→30.4 로 정상 범위(원본과 비슷한 22~34
대)로 돌아오고 안전상한 도달은 다시 0 이 된다.

**요약**: 두 변경 모두 승률을 낮추는 방향으로 작용했지만 크기가 다르다 — B
의 그립 수정 단독은 승률을 약 1/5(99.1%→77.7%, 21.4%p)만 깎으면서 그 대가로
정체 경기(안전상한 도달 11.8%, 평균 교환수 최대 62배)라는 별도 문제를
만들었고, AutoA 의 3중 안전장치는 그 정체 문제를 깨끗이 없애는 동시에(안전상한
0으로 복귀) 승률을 사실상 0에 가깝게(4.3%) 만드는 훨씬 큰 요인이다. 최종
붕괴(99.1%→4.3%, 총 94.7%p) 중 콤보2→콤보3 구간이 차지하는 몫은 **약
77%(73.4%p/94.7%p)**, 콤보1→콤보2 구간은 약 23%(21.4%p/94.7%p) — 즉 절대적
낙폭 대부분은 AutoA 개편 쪽에서 나왔다. 다만 이건 "AutoA 가 이제 그립 우위
없이도 파리티에서 공격하도록 강제됐다"는 설계 자체가 원인이라, AutoA 가
처음부터 최적/인간 수준 플레이가 아니었다는 기존 전제(§1 원본 문서)를
감안하면 "B 가 더 강해졌다"와 "A 가 원래 갖고 있던 인위적 그립 우위를
안전장치가 걷어냈다"를 이 데이터만으로는 더 못 쪼갠다 — 판단은 안 하고
숫자만 남긴다.

## §3 — 그립 파리티 동역학

끝내는지, 흔들기→기술 선언이 파리티 중에 나오면 득점까지 이어지는지 — 계측만,
결론 없음. **정의(이 세션이 고른 것, 정답이라 주장 안 함)**: 스트릭은 연속된

전 그립이 이미 0-0 이 아니게 바뀌어 있음(직전 교환의 그립 액션 결과). 굳히기 틱
