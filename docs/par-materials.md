### 1. 도메인 로직과 엔진의 컴파일 타임 분리 `[설계]`

- **P** — 격투 게임의 핵심은 판정 규칙(2단계 턴·상성표·상대 습관 로직)인데, MonoBehaviour 안에 두면 규칙 하나 확인하는 데도 에디터 Play 가 필요하고, 종목 확장(유도→복싱→킥복싱→MMA) 시 UI 째로 복제하게 된다.
- **A** — asmdef 로 `CounterTime.Core`(순수 C#, `noEngineReferences: true`)와 `CounterTime.Game`(MonoBehaviour/UI)을 분리, `Game → Core` 단방향 참조로 고정. ScriptableObject 가 UnityEngine 타입이라 Core 에 못 들어가는 문제는 **데이터(POCO)와 저작 도구(SO)를 분리**해 SO 를 Game 쪽 래퍼로 두는 방식으로 해결.
- **R** — 엔진 의존성이 규칙 코드에 섞이는 것을 컴파일러가 막는다. 에디터 실행 없이 EditMode 테스트로 판정 검증 가능한 구조.
- **면접 예상 질문** — "왜 폴더 분리가 아니라 asmdef 였나?" → 폴더는 `using UnityEngine;` 한 줄로 무너진다. 강제되지 않는 규칙은 지켜지지 않는다.
- 근거 문서: `docs/decisions/assembly-split-core-game.md`

### 2. Git LFS clean/smudge 필터 원인 규명 `[검증]`

- **P** — 건드리지 않은 텍스처가 `modified` 로 뜨고 diff 가 `Bin 24069 -> 130 bytes` 로 표시됨. 파일 손상으로 오해하기 쉬운 증상.
- **A** — 워킹 트리 파일이 실제로는 정상 이미지임을 헤더로 확인하고, LFS 의 clean 필터가 커밋 시점 raw blob 과 다른 130바이트 포인터를 산출하기 때문임을 규명. 원인이 "LFS 설정이 초기 커밋보다 늦게 들어간 것"임을 타임스탬프로 특정.
- **R** — 히스토리 재작성(`git lfs migrate import`)과 현행 유지를 비교해 **현행 유지**를 택했다. 원격에 이미 푸시된 상태라 재작성은 force push 를 요구하는데, 회수되는 건 24KB 튜토리얼 아이콘 하나였다. 대신 Unity 프로젝트 세팅 순서를 `.gitattributes 배치 → lfs install → git init → 첫 커밋` 으로 고정해 재발을 막았다.
- **면접 예상 질문** — "LFS 를 나중에 붙이면 왜 안 되나?" → 소급 적용되지 않는다. 히스토리의 blob 은 재작성 없이는 안 사라지고, 재작성 비용은 원격 푸시 여부·협업자 수에 비례해 오른다.
- **말할 가치가 있는 지점** — 처음엔 "지금이 재작성 비용 최저 시점"이라고 판단했다가, 원격 상태를 실제로 확인(`git ls-remote`)하고 전제가 틀렸음을 발견해 결론을 뒤집었다. 24KB를 위해 force push 하지 않는 쪽이 옳았다.
- 근거 문서: `docs/troubleshooting/lfs-after-first-commit.md`, `docs/decisions/git-lfs.md`

### 4. 설계한 아키텍처 경계를 실제 기능으로 증명 `[검증]`

- **P** — 08-03 에 asmdef 로 Core/Game 을 분리했지만 **설계뿐이었다.** 실제 기능을 붙이는 순간 경계가 지켜지는지는 미지수였다. 특히 시나리오 러너는 JSON 파싱(`JsonUtility`)·색 파싱(`ColorUtility`)·애니메이션 재생처럼 엔진 타입이 규칙 코드와 뒤엉키기 쉬운 기능이다.
- **A** — 경계를 세 지점에서 명시적으로 그었다. ① 데이터 타입은 Core 의 `[System.Serializable]` POCO 로 소유하고 `JsonUtility` 호출만 Game 의 Loader 에 격리 ② 테두리 색은 Core 가 **문자열로** 들고 `NodeKind` 분류만 수행, `Color` 변환은 Game ③ 모션은 Core 가 아예 모르게 하고 `NodeEntered` 이벤트만 발행, 매핑은 Game 쪽 ScriptableObject.
- **R** — 모션 연결 기능을 통째로 추가한 커밋(`992a77b`)에서 **`Scripts/Core/` diff 0줄.** 표현 기능을 붙이는데 도메인 코드를 한 줄도 안 건드렸다. `Scripts/Core/` 전체 grep 에 `UnityEngine` 0건 유지. Core 로직만 에디터에서 단독 실행해 JSON 파싱 → 그래프 구성 → 순회까지 Play 없이 검증.
- **면접 예상 질문** — "경계를 그었다는 걸 어떻게 증명하나?" → 기능 추가 커밋의 Core diff 가 0줄인지 본다. 말이 아니라 커밋으로 남는다.
- **말할 가치가 있는 지점** — 부수 소득으로 **특수 케이스 분기가 하나 사라졌다.** 보드의 범례 노드(n0)를 게임에서 빼야 했는데, 그래프를 데이터 그대로 만들고 러너 시작점만 n1 로 두니 n0 을 가리키는 엣지가 없어 자연히 도달 불가가 됐다. 제외 코드를 안 짜도 됐다.
- 근거 문서: `docs/decisions/scenario-runner-core-game-boundary.md`

### 5. 캡처로는 안 보이던 UI 오버플로를 수치 비교로 검출 `[검증]`

- **P** — Play 화면을 캡처해 눈으로 확인했을 때 UI 는 멀쩡해 보였다. 글자가 잘리지도, 깨지지도 않았다.
- **A** — 눈 대신 rect 높이와 `GetPreferredValues` / `textBounds.size.y` 를 비교했다. TMP 의 `overflowMode` 기본값이 `Overflow` 라 **rect 를 넘겨도 자르지 않고 그냥 그린다**는 것이 원인. 제목은 전 노드에서 7px, 본문 최장 노드는 10.5px 초과 중이었다. 오토사이즈가 구해줄 것이라는 가정도 검증했는데, 24 → 22.4pt 에서 멈추고 하한(14pt)까지 가지 않았다 — 강제로 6패스 돌려 수렴이 아니라 정착임을 확인.
- **R** — 폰트 크기(취향 영역)는 건드리지 않고 레이아웃 재배분으로 해결. TextPanel 152 → 190px. 8개 노드(본문 최장 5·선택지 최다 3·종단 3) 전부 통과. 부수적으로 본문이 오토사이즈 없이 원래 24pt 를 회복.
- **면접 예상 질문** — "왜 스크린샷으로 안 되나?" → `Overflow` 모드는 잘림이라는 증상을 만들지 않는다. 컨테이너 밖에 그려질 뿐이고, 마침 여백이 있으면 정상으로 보인다. 증상이 없는 결함은 수치로만 잡힌다.
- **말할 가치가 있는 지점** — `isTextOverflowing` 플래그가 `False` 를 반환하고 있었다. 프레임워크가 제공하는 상태 플래그를 믿고 넘어갔으면 못 잡았다.
- 근거 문서: `docs/troubleshooting/tmp-text-overflow.md`

### 6. 에디터 자동 검증 파이프라인의 거짓 음성 규명 `[검증]`

- **P** — Unity 에디터를 MCP 로 원격 제어해 Play 모드 결과를 사람 없이 검증하려 했는데, 검증 결과가 **다섯 군데서 거짓말을 했다.** 모션 연결이 통째로 안 되는 것처럼(전부 `Fight Idle`), 버튼이 클릭 불가인 것처럼(레이캐스트 0 히트), 한글 폰트가 깨진 것처럼(캡처가 전부 두부) 보였다.
- **A** — 전부 검증 도구 쪽 문제로 규명. ① 에디터가 포커스를 잃으면 Game 뷰가 프레임을 안 돌려 캡처가 생성되지 않음 → `Application.runInBackground` 를 **코루틴이 아닌 에디터 스레드에서** 설정 ② `CrossFade`·신규 UI 그래픽은 다음 프레임에 반영되므로 같은 호출에서 읽으면 이전 값 → 코루틴으로 프레임을 넘기거나 호출을 분리 ③ 렌더 파이프라인을 우회한 RenderTexture 캡처는 동적 폰트 아틀라스가 GPU 에 안 올라간 상태를 찍음 → 실제 Game 뷰 프레임만 신뢰.
- **R** — 오탐을 걸러내는 6항목 체크리스트로 정리. 이후 노드↔모션 연결에서 대표 11개 노드의 전환 대상 100% 일치, 원샷 자동 복귀, 유지 상태 지속을 사람 개입 없이 확인.
- **면접 예상 질문** — "자동 검증을 신뢰할 수 있나?" → 도구가 만든 거짓 음성을 실제 결함과 구분하는 절차가 있어야 신뢰할 수 있다. RenderTexture 캡처만 봤으면 멀쩡한 폰트 설정을 갈아엎었을 것이다.
- **말할 가치가 있는 지점** — 실제 결함(버튼 누적 버그)과 도구 아티팩트(레이캐스트 0 히트)가 **같은 원인, 즉 프레임 타이밍**에서 나왔다. 하나는 고쳐야 하고 하나는 무시해야 한다. 이 구분이 자동 검증의 핵심이었다.
- 근거 문서: `docs/troubleshooting/mcp-play-mode-verification.md`

### 9. 에셋 참조 무결성을 커밋 경계에서 검증 `[검증]`

- **P** — 애니메이터 컨트롤러 2개는 커밋됐는데 그 컨트롤러가 참조하는 클립 4개가 미추적 상태였다. Unity 는 에셋을 guid 로 참조하고 guid 는 미추적 `.meta` 안에만 있었다. **내 PC 에서는 정상 동작하고, 컴파일 에러도 콘솔 경고도 없다.** 클론한 사람이 Play 로 해당 노드에 도달했을 때 캐릭터가 가만히 서 있는 것으로만 드러나는 무음 실패다.
- **A** — 원인을 `git add -u` 의 동작으로 특정했다. 도구가 만든 파일이 기존 경로(컨트롤러, 추적 중)와 신규 경로(클립, 미추적)로 흩어져, 참조하는 쪽만 스테이징되고 참조되는 쪽이 빠지는 조건이 정확히 성립했다. 커밋 전에 각 `.meta` 의 guid 를 뽑아 컨트롤러 안에서 실제로 해소되는지 대조하는 절차를 만들어 4개 전부 양쪽 컨트롤러에서 참조 중임을 확인하고 같은 커밋에 넣었다. 폴더 자체의 `.meta` 도 함께 — 빠뜨리면 다른 PC 에서 guid 가 새로 생겨 영구 diff 가 된다.
- **R** — 참조 끊김이 원격에 나가기 전에 차단. "참조하는 쪽과 참조되는 쪽이 다른 폴더면 `git add -u` 를 믿지 않는다"를 규칙으로 남겼다. 씬·프리팹·ScriptableObject 전부 같은 구조라 재사용된다.
- **면접 예상 질문** — "테스트나 CI 로 잡을 수 없나?" → 잡을 수 있지만 이건 **커밋 내용 자체의 결함**이라 빌드 이전 단계다. 워킹 트리에 파일이 있는 한 어떤 로컬 검증도 통과한다. 커밋된 것만으로 재구성했을 때 성립하는지를 별도로 봐야 한다.
- **말할 가치가 있는 지점** — 증상이 나타나는 시점이 커밋도 클론도 아니고 "그 노드에 도달했을 때"라는 점. 발견이 늦을수록 원인에서 멀어지는 종류의 결함이다.
- 근거 문서: `docs/troubleshooting/unity-asset-commit-boundary.md`

### 10. 라이브러리에 없는 종목 특화 에셋의 조달 범위 결정 `[적용 — Play 검증 전]`

- **P** — Mixamo 무료 라이브러리에는 격투 일반 동작만 있고 **유도 기술 모션이 없다.** 그 결과 굳히기·조르기 국면(승부가 갈리는 지점)에 서 있는 `Taunt` 모션이 붙어 있었다. 종목 순서가 유도→복싱→킥복싱→MMA 인데 첫 종목부터 라이브러리로 못 채운다는 뜻이었다.
- **A** — 모캡(비용 과다)과 라이브러리 재탐색(대상 부재)을 배제하고 AI 생성을 택하되, **생성 개수를 시나리오 등장 빈도로 결정했다.** 노드 43개를 분석하니 기술별 클립은 최소 8종이 필요했는데, 던지는 쪽과 달리 **당하는 쪽 모션은 기술이 무엇이든 유사**하다는 점을 이용해 낙법 1종을 공용화하고 던지기는 최빈 2종으로 좁혀 4종(20 크레딧)으로 확정. 정확히 맞지 않는 1건(n10 허리후리기 ← 밭다리 클립)은 "틀린 유도 기술이 안 유도 기술보다 가깝다"는 기준으로 임시 허용하되, STATUS.md 에 `알려진 공백` 섹션을 신설해 임시라는 사실이 소멸하지 않게 했다.
- **R** — 19개 노드 25개 State 교체, 크레딧은 기술별 생성 대비 절반 이하. 되돌림 경로를 위해 수정 전 스냅샷 커밋을 먼저 남겼다. **Play 검증은 아직 0** — 파일 레벨 확인만 마쳤다.
- **면접 예상 질문** — "AI 생성 에셋의 품질은 어떻게 보증하나?" → 보증 안 한다. 프로토타입 단계에서 필요한 건 "유도처럼 보이는 것"이지 경기 영상 수준이 아니고, 모캡으로 교체할 지점을 문서에 남겨 뒀다. 품질 기준을 단계에 맞추는 것과 품질을 포기하는 것은 다르다.
- **말할 가치가 있는 지점** — 문서를 쓰며 파일을 다시 읽다가 **4개 클립 전부 Loop ON, 8개 State 전부 exit 트랜지션 없음**을 발견했다. 이틀 전 스스로 세운 규칙(원샷은 Loop OFF + 자동 복귀)과 어긋나 업어치기 진입이 무한 반복되는 설정이다. 새 에셋이 기존 컨벤션을 물려받는지는 자동으로 보장되지 않는다.
- 근거 문서: `docs/decisions/ai-generated-motion-clips.md`

### 소재화하지 않기로 한 것

- `Assets/Editor/HubForceResolve.cs` 삭제 건 — 스크립트 전문 확인 결과 Unity Hub 부트스트랩이 `Client.Resolve()` 후 **스스로 삭제한 것**이었다. 사람이 문제를 겪고 해결한 흔적이 아니므로 소재로 쓰지 않는다. (없는 문제를 소재로 만들면 면접에서 바로 무너진다)
- MCP `Unity_Camera_Capture` 에 `cameraInstanceID` 를 넘기면 항상 실패하는 건 — 툴 자체의 한계고 우회(인자 없이 호출)가 즉시 통했다. 규명한 것도 해결한 것도 없다. 일지에 한 줄로 남기는 걸로 충분.
- 노드↔모션 매핑 36개를 채운 작업 — 분량은 많지만 판단의 난이도가 아니라 성실함의 영역이다. 소재로 쓰면 "텍스트 읽고 표 채웠다"가 된다. 대신 **매핑을 Core 밖으로 뺀 설계 판단**(4번)이 소재다.
- 08-07 의 19개 노드 재매핑도 같은 이유로 제외 — 위와 같은 성격의 작업이다. 소재는 **무엇을 몇 개 만들지 정한 판단**(10번)이지 표를 채운 것이 아니다. (A/B 시전자 구분이나 n41 의 좌우 반전 같은 건 꼼꼼함이지 설계가 아니다)
