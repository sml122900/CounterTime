### 1. 도메인 로직과 엔진의 컴파일 타임 분리 `[설계]`

- **P** — 격투 게임의 핵심은 판정 규칙(2단계 턴·상성표·상대 습관 로직)인데, MonoBehaviour 안에 두면 규칙 하나 확인하는 데도 에디터 Play 가 필요하고, 종목 확장(유도→복싱→킥복싱→MMA) 시 UI 째로 복제하게 된다.
- **A** — asmdef 로 `CounterTime.Core`(순수 C#, `noEngineReferences: true`)와 `CounterTime.Game`(MonoBehaviour/UI)을 분리, `Game → Core` 단방향 참조로 고정. ScriptableObject 가 UnityEngine 타입이라 Core 에 못 들어가는 문제는 **데이터(POCO)와 저작 도구(SO)를 분리**해 SO 를 Game 쪽 래퍼로 두는 방식으로 해결.
- **R** — 엔진 의존성이 규칙 코드에 섞이는 것을 컴파일러가 막는다. 에디터 실행 없이 EditMode 테스트로 판정 검증 가능한 구조.
- **면접 예상 질문** — "왜 폴더 분리가 아니라 asmdef 였나?" → 폴더는 `using UnityEngine;` 한 줄로 무너진다. 강제되지 않는 규칙은 지켜지지 않는다.
- 근거 문서: `docs/decisions/assembly-split-core-game.md`

### 2. Git LFS clean/smudge 필터 원인 규명 `[검증]`

- **P** — 건드리지 않은 텍스처가 `modified` 로 뜨고 diff 가 `Bin 24069 -> 130 bytes` 로 표시됨. 파일 손상으로 오해하기 쉬운 증상.
- **A** — 워킹 트리 파일이 실제로는 정상 이미지임을 헤더로 확인하고, LFS 의 clean 필터가 커밋 시점 raw blob 과 다른 130바이트 포인터를 산출하기 때문임을 규명. 원인이 "LFS 설정이 초기 커밋보다 늦게 들어간 것"임을 타임스탬프로 특정.
- **R** — 히스토리 재작성(`git lfs migrate import`)과 현행 유지를 비교해 **현행 유지**를 택했다. 원격에 이미 푸시된 상태라 재작성은 force push 를 요구하는데, 회수되는 건 24KB 튜토리얼 아이콘 하나였다. 대신 Unity 프로젝트 세팅 순서를 `.gitattributes 배치 → lfs install → git init → 첫 커밋` 으로 고정해 재발을 막았다.
- **면접 예상 질문** — "LFS 를 나중에 붙이면 왜 안 되나?" → 소급 적용되지 않는다. 히스토리의 blob 은 재작성 없이는 안 사라지고, 재작성 비용은 원격 푸시 여부·협업자 수에 비례해 오른다.
- **말할 가치가 있는 지점** — 처음엔 "지금이 재작성 비용 최저 시점"이라고 판단했다가, 원격 상태를 실제로 확인(`git ls-remote`)하고 전제가 틀렸음을 발견해 결론을 뒤집었다. 24KB를 위해 force push 하지 않는 쪽이 옳았다.
- 근거 문서: `docs/troubleshooting/lfs-after-first-commit.md`, `docs/decisions/git-lfs.md`

### 4. 설계한 아키텍처 경계를 실제 기능으로 증명 `[검증]`

- **P** — 08-03 에 asmdef 로 Core/Game 을 분리했지만 **설계뿐이었다.** 실제 기능을 붙이는 순간 경계가 지켜지는지는 미지수였다. 특히 시나리오 러너는 JSON 파싱(`JsonUtility`)·색 파싱(`ColorUtility`)·애니메이션 재생처럼 엔진 타입이 규칙 코드와 뒤엉키기 쉬운 기능이다.
- **A** — 경계를 세 지점에서 명시적으로 그었다. ① 데이터 타입은 Core 의 `[System.Serializable]` POCO 로 소유하고 `JsonUtility` 호출만 Game 의 Loader 에 격리 ② 테두리 색은 Core 가 **문자열로** 들고 `NodeKind` 분류만 수행, `Color` 변환은 Game ③ 모션은 Core 가 아예 모르게 하고 `NodeEntered` 이벤트만 발행, 매핑은 Game 쪽 ScriptableObject.
- **R** — 모션 연결 기능을 통째로 추가한 커밋(`992a77b`)에서 **`Scripts/Core/` diff 0줄.** 표현 기능을 붙이는데 도메인 코드를 한 줄도 안 건드렸다. `Scripts/Core/` 전체 grep 에 `UnityEngine` 0건 유지. Core 로직만 에디터에서 단독 실행해 JSON 파싱 → 그래프 구성 → 순회까지 Play 없이 검증.
- **면접 예상 질문** — "경계를 그었다는 걸 어떻게 증명하나?" → 기능 추가 커밋의 Core diff 가 0줄인지 본다. 말이 아니라 커밋으로 남는다.
- **말할 가치가 있는 지점** — 부수 소득으로 **특수 케이스 분기가 하나 사라졌다.** 보드의 범례 노드(n0)를 게임에서 빼야 했는데, 그래프를 데이터 그대로 만들고 러너 시작점만 n1 로 두니 n0 을 가리키는 엣지가 없어 자연히 도달 불가가 됐다. 제외 코드를 안 짜도 됐다.
- 근거 문서: `docs/decisions/scenario-runner-core-game-boundary.md`

### 5. 캡처로는 안 보이던 UI 오버플로를 수치 비교로 검출 `[검증]`

- **P** — Play 화면을 캡처해 눈으로 확인했을 때 UI 는 멀쩡해 보였다. 글자가 잘리지도, 깨지지도 않았다.
- **A** — 눈 대신 rect 높이와 `GetPreferredValues` / `textBounds.size.y` 를 비교했다. TMP 의 `overflowMode` 기본값이 `Overflow` 라 **rect 를 넘겨도 자르지 않고 그냥 그린다**는 것이 원인. 제목은 전 노드에서 7px, 본문 최장 노드는 10.5px 초과 중이었다. 오토사이즈가 구해줄 것이라는 가정도 검증했는데, 24 → 22.4pt 에서 멈추고 하한(14pt)까지 가지 않았다 — 강제로 6패스 돌려 수렴이 아니라 정착임을 확인.
- **R** — 폰트 크기(취향 영역)는 건드리지 않고 레이아웃 재배분으로 해결. TextPanel 152 → 190px. 8개 노드(본문 최장 5·선택지 최다 3·종단 3) 전부 통과. 부수적으로 본문이 오토사이즈 없이 원래 24pt 를 회복.
- **면접 예상 질문** — "왜 스크린샷으로 안 되나?" → `Overflow` 모드는 잘림이라는 증상을 만들지 않는다. 컨테이너 밖에 그려질 뿐이고, 마침 여백이 있으면 정상으로 보인다. 증상이 없는 결함은 수치로만 잡힌다.
- **말할 가치가 있는 지점** — `isTextOverflowing` 플래그가 `False` 를 반환하고 있었다. 프레임워크가 제공하는 상태 플래그를 믿고 넘어갔으면 못 잡았다.
- 근거 문서: `docs/troubleshooting/tmp-text-overflow.md`

### 6. 에디터 자동 검증 파이프라인의 거짓 음성 규명 `[검증]`

- **P** — Unity 에디터를 MCP 로 원격 제어해 Play 모드 결과를 사람 없이 검증하려 했는데, 검증 결과가 **다섯 군데서 거짓말을 했다.** 모션 연결이 통째로 안 되는 것처럼(전부 `Fight Idle`), 버튼이 클릭 불가인 것처럼(레이캐스트 0 히트), 한글 폰트가 깨진 것처럼(캡처가 전부 두부) 보였다.
- **A** — 전부 검증 도구 쪽 문제로 규명. ① 에디터가 포커스를 잃으면 Game 뷰가 프레임을 안 돌려 캡처가 생성되지 않음 → `Application.runInBackground` 를 **코루틴이 아닌 에디터 스레드에서** 설정 ② `CrossFade`·신규 UI 그래픽은 다음 프레임에 반영되므로 같은 호출에서 읽으면 이전 값 → 코루틴으로 프레임을 넘기거나 호출을 분리 ③ 렌더 파이프라인을 우회한 RenderTexture 캡처는 동적 폰트 아틀라스가 GPU 에 안 올라간 상태를 찍음 → 실제 Game 뷰 프레임만 신뢰.
- **R** — 오탐을 걸러내는 6항목 체크리스트로 정리. 이후 노드↔모션 연결에서 대표 11개 노드의 전환 대상 100% 일치, 원샷 자동 복귀, 유지 상태 지속을 사람 개입 없이 확인.
- **면접 예상 질문** — "자동 검증을 신뢰할 수 있나?" → 도구가 만든 거짓 음성을 실제 결함과 구분하는 절차가 있어야 신뢰할 수 있다. RenderTexture 캡처만 봤으면 멀쩡한 폰트 설정을 갈아엎었을 것이다.
- **말할 가치가 있는 지점** — 실제 결함(버튼 누적 버그)과 도구 아티팩트(레이캐스트 0 히트)가 **같은 원인, 즉 프레임 타이밍**에서 나왔다. 하나는 고쳐야 하고 하나는 무시해야 한다. 이 구분이 자동 검증의 핵심이었다.
- 근거 문서: `docs/troubleshooting/mcp-play-mode-verification.md`

### 9. 에셋 참조 무결성을 커밋 경계에서 검증 `[검증]`

- **P** — 애니메이터 컨트롤러 2개는 커밋됐는데 그 컨트롤러가 참조하는 클립 4개가 미추적 상태였다. Unity 는 에셋을 guid 로 참조하고 guid 는 미추적 `.meta` 안에만 있었다. **내 PC 에서는 정상 동작하고, 컴파일 에러도 콘솔 경고도 없다.** 클론한 사람이 Play 로 해당 노드에 도달했을 때 캐릭터가 가만히 서 있는 것으로만 드러나는 무음 실패다.
- **A** — 원인을 `git add -u` 의 동작으로 특정했다. 도구가 만든 파일이 기존 경로(컨트롤러, 추적 중)와 신규 경로(클립, 미추적)로 흩어져, 참조하는 쪽만 스테이징되고 참조되는 쪽이 빠지는 조건이 정확히 성립했다. 커밋 전에 각 `.meta` 의 guid 를 뽑아 컨트롤러 안에서 실제로 해소되는지 대조하는 절차를 만들어 4개 전부 양쪽 컨트롤러에서 참조 중임을 확인하고 같은 커밋에 넣었다. 폴더 자체의 `.meta` 도 함께 — 빠뜨리면 다른 PC 에서 guid 가 새로 생겨 영구 diff 가 된다.
- **R** — 참조 끊김이 원격에 나가기 전에 차단. "참조하는 쪽과 참조되는 쪽이 다른 폴더면 `git add -u` 를 믿지 않는다"를 규칙으로 남겼다. 씬·프리팹·ScriptableObject 전부 같은 구조라 재사용된다.
- **면접 예상 질문** — "테스트나 CI 로 잡을 수 없나?" → 잡을 수 있지만 이건 **커밋 내용 자체의 결함**이라 빌드 이전 단계다. 워킹 트리에 파일이 있는 한 어떤 로컬 검증도 통과한다. 커밋된 것만으로 재구성했을 때 성립하는지를 별도로 봐야 한다.
- **말할 가치가 있는 지점** — 증상이 나타나는 시점이 커밋도 클론도 아니고 "그 노드에 도달했을 때"라는 점. 발견이 늦을수록 원인에서 멀어지는 종류의 결함이다.
- 근거 문서: `docs/troubleshooting/unity-asset-commit-boundary.md`

### 10. 라이브러리에 없는 종목 특화 에셋의 조달 범위 결정 `[적용 — Play 검증 전]`

### 12. 자기참조 때문에 성립하지 않는 요구사항을 재설계 `[적용 — 훅으로 자동 유지]`

- **P** — "문서에 커밋 해시 스탬프를 넣고 편집과 같은 커밋에서 갱신하라"는 요구를 받았다. **성립하지 않는다.** 커밋 해시는 그 커밋의 내용에서 나오는데, 해시를 파일에 쓰면 내용이 바뀌고 해시가 바뀐다. 수렴하지 않는다. 더 나쁜 건 커밋 해시가 **커밋된 것에 대해서만** 말한다는 점이다 — 워킹 트리에서 고치고 커밋 안 한 사본은 스탬프가 여전히 정상이라고 말한다. **스탬프의 존재 이유였던 실패를 정확히 못 잡는 장치.**
- **A** — 요구를 거부하지 않고 **목적을 유지한 채 측정 대상을 바꿨다.** 해시 대상을 커밋이 아니라 "1행을 제외한 본문"으로 옮겼다. 1행이 계산에서 빠지므로 스탬프를 쓰는 행위가 스탬프가 재는 대상을 바꾸지 않는다 — 첫 시도에 수렴하고 사람의 판단이 0이다. 부수 이득이 더 컸다: 저장소 없이 **파일 하나만으로** 진위 확인이 된다. 유지는 저장소에 커밋한 pre-commit 훅에 맡기고, 새 클론에서 CRLF 로 셔뱅이 깨지지 않게 `.gitattributes` 에 `*.sh`·`tools/githooks/*` 를 `eol=lf` 로 고정했다.
- **R** — 첫 실행에 수렴, 재실행은 멱등, `--check` 는 실제 stale 만 exit 1. 실제 커밋을 관통시켜 검증(`a24d23c`→`c9290de`). 훅이 안 돌아도 스탬프는 **틀린 값이 아니라 낡은 값**이 되고 낡음은 읽는 시점에 드러난다 — 침묵하는 오류가 아니라 사용 시점에 드러나는 지연이라, 대응은 세션 시작 점검 한 줄로 충분하다고 판단했다.
- **면접 예상 질문** — "요구가 잘못됐으면 그냥 안 된다고 하면 되지 않나?" → 요구의 **목적**(사본이 진짜인지 확인)은 타당했고 구현 수단만 성립하지 않았다. 목적을 남기고 수단을 바꾸는 게 맞다. 실제로 바꾼 쪽이 원래 요구보다 탐지 범위가 넓다.
- 근거 문서: `docs/decisions/body-hash-doc-stamp.md`

(1) 초반에 조건이 서는 습관이 없어서 관측이 0 → 진입 습관 신설, (2) 확정에 4번째 발화가 필요한데 폐기는 2회면 나서 **벌줄 수 있는 습관이 읽히기 전에 사라지는 산술적 불가능** → 피해는 확정 뒤부터, (3) 판정의 절반이 폴백에서 나와 읽을 수 없는 던지기 → 폴백은 큰기술 금지. 사다리 1~5행 0회 → 11회, 폴백 88% → 36%, 확정 도달 0/5 → 4/5. 재발 감시로 `ReadLadderActuallyRuns_NotEveryTurnIsNeutral` 하나만 "0이면 실패"로 남겼다.
- **면접 예상 질문** — "테스트가 145개 초록인데 시스템이 안 돌았다는 게 말이 되나?" → 된다. 사다리 6행 각각에 테스트가 있었고 전부 통과했다. **한 경기에서 1~5행이 0회라는 것은 어느 단위 테스트의 실패도 아니다.** 단위 테스트는 의도한 것을 지키고, 통합 계측은 의도하지 않은 것을 잡는다.
- **말할 가치가 있는 지점** — 예상 부작용을 두 번 내걸었고 **두 번 다 실측이 부정했다.** "큰기술을 빼면 B 가 소극으로 몰려 지도로 질 것" → 견제기가 §6.1 진입 −2 를 계속 넣어 세 프로필 전부 지도 3 종료 0. "그쳐가 잡기를 풀면 간판 습관 발화가 줄 것" → 오히려 늘었다(경기가 길어져 잡기를 다시 세울 기회도 같이 늘었다). 예측을 적어두고 실측으로 채점한 것이 매번 남는 게 있었다.
- 근거 문서: `docs/decisions/measurement-driven-rules.md`, `docs/troubleshooting/read-system-silently-dead.md`

### 16. 동작 보존 리팩터링을 "전량 지문 diff" 로 강제 `[검증 — 26커밋 IDENTICAL]`

- **P** — 회귀 기준선(대조 모드: 42노드 참조 경기 + 130 테스트)에 **값을 공급하는 계층을 통째로 갈아끼우는** 작업이었다. 요구는 "동작이 1비트라도 바뀌면 잘못한 것". 문제는 이번에 건드리는 것 — 러너 실행 순서, 커밋 생성 지점, 읽기 값 주입 지점 — 이 **어느 단위 테스트도 직접 단언하지 않는다**는 것. 130개를 초록으로 둔 채 통과할 수 있는 회귀를 셋 열거할 수 있었다(잡기 이벤트 순서, 자세 유지 규칙, 교환당 시계).
- **A** — 메인라인 17노드를 실제 러너로 걷게 하고 **모든 `MatchEvent` + 각 노드 직후 엔진 전체 상태**를 52행 지문으로 떠서 단계마다 diff 했다. 요약값이 아니라 **전량**이어야 위 셋을 다 잡는다. 러너가 `MonoBehaviour` 라 헤드리스로 못 도는 문제는 UnityEngine **셰임 60줄**(로깅·클램프·JSON·기반 클래스만)로 풀었다 — 규칙은 한 줄도 재구현하지 않아 **저장소 파일 그대로** 컴파일된다. 수정 전/후를 `git stash` 로 둘 다 돌려 비교했다.
- **R** — asmdef 신설·인터페이스 3종 추출·클래스 개명·러너 배선 변경, **그리고 Core 규칙 변경(v3.4)** 까지 26커밋 내내 IDENTICAL. 실제로 잡은 것도 있다 — 1단계 `using` 누락을 Unity 켜기 전에 컴파일 에러로, 0.5단계에서는 파싱 거부 경로의 out 값이 37개 노드에서 틀린 값이라는 것을 **전수로** 확인해 그 불변식을 커밋되는 테스트로 옮겼다.
- **면접 예상 질문** — "셰임으로 돌린 게 진짜 검증인가?" → 셰임이 **무엇을** 공급하는지가 답을 가른다. 규칙을 셰임했으면 검증이 아니다. 그리고 셰임이 못 덮는 영역은 하니스가 **스스로 범위를 밝히게** 해뒀다 — 마지막 줄이 "MatchRunnerHandActionTests (3) is NOT run here" 를 출력한다. 범위를 넘겨짚지 않는 것이 이 도구의 전제다.
- **말할 가치가 있는 지점** — 이 방식의 진짜 비용은 **지문 자체가 회귀 대상이 된다**는 것이다. 계측 3행을 추가한 회차에 지문 형식이 바뀌어 diff 가 거짓 양성을 냈다. 그래서 경계를 나눴다 — **엔진이 낸 것만 지문에 들어가고, 내가 궁금해서 찍는 값은 지문 범위 밖에 출력한다.** 계측을 늘려도 기준선이 안 흔들린다.
- 근거 문서: `docs/decisions/behavior-fingerprint-refactor.md`

### 17. 잘못된 상태를 "테스트로 잡기" 대신 "표현 불가능하게" 만든 것 `[적용]`

- **P** — 습관 정의 타입이 경기 상태(피해 카운터·폐기 플래그)를 같이 들고 있었다. Unity 의 ScriptableObject 는 **플레이 모드 중 변경이 에셋에 남는** 물건이라, 에셋 한 장을 여러 경기가 물면 지난 경기의 폐기가 **에러 없이** 다음 경기로 따라붙는다. 처음엔 "경기마다 `Create` 를 다시 부른다"는 규약과 그걸 확인하는 테스트로 막았다.
- **A** — 규약이 아니라 **타입으로** 갈랐다. `HabitDefinition`·`OpponentDefinition` 을 불변으로(공개 필드 전부 `readonly`, 공개 setter 0) 만들고 경기당 상태를 `HabitState` 로 분리했다. 같은 원칙을 다른 두 곳에도 적용했다 — 관측 원장의 `Record` 는 `bool` 이 아니라 `HabitDecision` 을 받아 "조건만 성립한 턴은 안 센다"를 **호출 규약이 아니라 구조**로 세웠고, `RegisterDamage` 는 원장을 받아 확정 검사를 안에 뒀다.
- **R** — 이제 경기 간 오염을 일으키려면 누군가 **정의 타입에 새 필드를 만들어야** 한다. 리플렉션 테스트가 그 경계를 지킨다(쓰기 가능한 공개 필드 0 / 공개 setter 0). 기존 테스트는 살려두되 의미를 "`Create` 를 두 번 불렀나"에서 **"정의 한 장을 공유해도 깨끗한가"** 로 옮겼다 — 실제로 일어나는 실수가 그쪽이다.
- **면접 예상 질문** — "테스트가 있으면 충분하지 않나?" → 테스트는 **내가 상상한 실수**를 잡는다. 여기서 막으려는 건 "SO 를 그대로 물려 쓰는 것"인데, 그건 실수가 아니라 **Unity 에서 자연스러운 사용법**이다. 자연스러운 사용법이 조용히 깨지는 구조라면 테스트가 아니라 타입을 고쳐야 한다.
- 근거 문서: `docs/daily/2026-08-10.md`

### 18. 인터페이스 면을 좁게 동결하고, 넓힐 요구가 왔을 때 쪼갠 것 `[적용]`

- **P** — 브레인이 경기 상태를 읽어야 하는데, 읽기 전용 뷰를 넓게 열면 그것만으로 "습관 기반"이 아니라 "상태 평가형 AI" 로 흐른다. 그건 설계에서 명시적으로 배제된 안이었다.
- **A** — 습관 조건용 면(`IHabitContext`)을 **4개 멤버로 동결**하고, 각 멤버가 어느 습관 때문에 필요한지 1:1 로 문서화했다. 뺀 것도 이유와 함께 적었다 — 지도 *개수*(습관이 보는 건 최근성이지 개수가 아니다), 시계, 심판 누산기(규칙이 숫자 노출을 금지). 이후 폴백이 "지도수·시계로 가중"을 요구했을 때 **이 면을 넓히지 않고 별도 인터페이스를 신설**했다.
- **R** — 경계를 **타입으로** 막았다. 습관 조건 델리게이트의 인자가 `IHabitContext` 라 다른 면이 들어올 수 없다. 그 위에 (1) 델리게이트 시그니처, (2) 멤버가 정확히 넷인지, (3) 폴백 전용 멤버 4개가 거기 **없는지**를 리플렉션으로 고정하고, 마지막으로 `IHabitContext` **만** 구현한 객체로 실제 조건들을 호출한다 — 누가 안에서 캐스팅하면 거기서 터진다.
- **면접 예상 질문** — "인터페이스를 왜 둘로 쪼개나, 한 객체가 둘 다 구현하는데?" → 구현체가 하나인 것과 **면이 둘인 것은 다르다.** 습관 조건은 `IHabitContext` 타입으로만 그 객체를 받으므로 나머지가 보이지 않는다. 그리고 이름도 신경 썼다 — 하드 게이트는 사다리 **전체**에 걸리는데 인터페이스 이름에 "fallback" 이 들어가면 "게이트는 폴백 단에만 적용된다"는 오독을 부르고, 그 오독은 곧 오작동이다.
- **말할 가치가 있는 지점** — 면을 동결한 대가로 **"멤버를 추가하려면 보고한다"가 절차의 일부**가 됐다. 실제로 3단계에서 그 요구가 왔고, 넓히는 대신 쪼갠 것이 이번 세션에서 가장 값이 컸던 판단이다. 넓혔으면 `IHabitContext` 가 6개, 다음엔 8개가 되고 습관이 상태 평가형으로 흐르는 걸 아무도 못 막는다.
- 근거 문서: `docs/daily/2026-08-10.md`, `md/OPPONENT_BRAIN.md` §4

### 19. 부수효과 호출 시점의 소유권을 결정자에서 소비자로 옮긴 것 `[해결]`

- **P** — 습관 브레인이 "이번 턴 무엇을 낼지" 결정하는 즉시 읽기 리졸버에 알렸다. 결정 시점과 그 결정이 교환에 실제로 제출되는 시점이 같다는 암묵의 가정 위에 서 있었는데, 쿠즈시 선행 데코레이터가 "이미 나온 결정을 한 턴 버퍼링해서 늦게 내보내는" 기능을 넣으면서 그 가정이 깨졌다. 관측값은 안 틀렸지만 시점이 한 교환 당겨져 있었다 — 테스트도 컴파일도 전부 통과한 채로 존재한 결함이었다.
- **A** — 결정을 내리는 클래스에서 알림 호출 자체를 제거하고, 그 결정을 소비하는 지점(실제로 교환을 만드는 코드)으로 호출을 옮겼다. 결정자는 "지금 무엇을 결정했는지"만 노출하고, "언제 그게 유효한지"는 그걸 아는 소비자가 판단하게 했다 — 감싸는 데코레이터는 한 글자도 안 건드렸다.
- **R** — 쿠즈시 설치 교환엔 알림이 안 가고 다음 교환(진짜 결정 제출)에만 가는 것을 실제 읽기 결과값으로 고정하는 테스트를 새로 추가. 202/202 그린, 동작 보존 지문(fingerprint) IDENTICAL — 대조 모드는 이 경로를 안 타므로 무변화, 사다리·카탈로그 파일은 diff 0줄.
- **면접 예상 질문** — "왜 결정하는 쪽이 직접 안 부르게 했나?" → 그 클래스는 자기 반환값이 나중에 감싸일 수 있다는 걸 모른다. 부수효과의 타이밍을 그 부수효과가 언제 유효한지 모르는 곳에 두면, 누가 감싸는 순간 조용히 깨진다.
- **말할 가치가 있는 지점** — 실행 계측이 아니라 코드를 다시 읽다가 발견한 결함이다. 200개 테스트가 전부 그린인 상태에서 "타이밍이 한 박자 어긋나 있다"는 건 실행 결과로는 안 드러나고 설계를 다시 읽어야 보인다.
- 근거 문서: `docs/decisions/habit-observation-call-site-ownership.md`

### 20. 런타임 생성 UI의 누락 컴포넌트를 실행 전에 코드 재검토로 잡은 것 `[해결]`

- **P** — 씬 파일 없이 코드로 캔버스를 만드는 UI 컴포넌트가 있었는데, `Canvas`/`CanvasScaler`만 만들고 `GraphicRaycaster`가 빠져 있었다. 이게 없으면 버튼이 몇 개든 클릭이 전혀 안 먹는다 — 에러도 경고도 없이 조용히 반응 없는 화면이 된다. 이 컴포넌트는 컴파일 확인까지만 됐을 뿐 Play 모드로 한 번도 실행되지 않은 상태였다.
- **A** — Play 모드 진입 준비를 자동화하는 에디터 메뉴를 만들다가 코드를 다시 읽으며 발견했다. 그 시점엔 원인 파일을 고칠 권한이 없어(코드 변경 범위가 제한된 지시), 먼저 에디터 툴링으로 Play 진입 직후 컴포넌트를 붙이는 우회책을 짜서 증상을 막고 원인을 보고했다. 범위가 풀리자 원인 지점(캔버스 생성 코드)에 정식 수정을 반영하고 우회 코드를 삭제했다.
- **R** — 씬 에디터의 "Add Component 시 자동으로 딸려오는 컴포넌트" 관습이 코드로 만드는 경로엔 없다는 걸 실행 전에 잡아, 사람이 처음 Play를 누르는 순간 헛수고할 뻔한 걸 막았다. 우회에서 정식 수정으로 넘어가며 빌드에서도 동작하게 됐다(에디터 전용 우회는 빌드에 안 들어간다).
- **면접 예상 질문** — "컴파일도 되고 타입 로드도 확인됐는데 왜 못 잡았나?" → 둘 다 런타임 인터랙션을 검증하지 않는다. Play 모드 실행 확인이 사람 몫으로 미뤄진 컴포넌트는 그 확인 전까지 "동작 미검증"으로 다뤄야 한다는 근거가 됐다.
- 근거 문서: `docs/troubleshooting/livematch-canvas-missing-graphicraycaster.md`

### 21. "코드가 맞다"와 "그 문구를 써도 되는가"를 분리해서 다룬 것 `[해결]`

- **P** — 서술 문구 하나("같은 밭다리, 세 번째. B가 되받는다")를 특정 판정 키에 등록할지가 판단 대기로 남아 있었다. 실측해보니 실제 실행 경로(플레이 모드)에서 그 키에 물리는 기술명이 문서가 지시한 값과 정확히 일치했다 — 즉 "코드가 이 키를 쓰는 게 맞다"는 확인됐다.
- **A** — 그 확인과는 별개로, 문구 자체가 발생 횟수("세 번째")를 명시하고 있어서 실제로는 몇 번째 발생이든 뜨는 이 키에 물리면 오정보가 된다는 걸 짚었다. "코드 경로가 일치하는가"라는 질문과 "그 결과로 나온 문구가 사용자에게 맞는 정보인가"라는 질문을 같은 것으로 뭉치지 않고 따로 보고했다.
- **R** — 최종 결정은 실측 결과(일치)와 무관하게 그 키를 등록 해제하고 폴백으로 되돌리는 쪽이었다 — 실측이 첫 번째 질문에 "맞다"고 답했다고 두 번째 질문까지 자동으로 "맞다"가 되는 게 아니었다.
- **면접 예상 질문** — "실측이 일치한다고 나왔으면 그대로 쓰면 되는 거 아닌가?" → 실측은 "코드가 어떻게 동작하는가"를 답하지 "그 결과가 사용자에게 옳은 정보인가"는 안 답한다. 후자는 문구의 내용을 따로 봐야 한다 — 이번 경우 문구가 전제하는 상황(세 번째 반복)이 실행 경로가 보장하는 상황(몇 번째든)보다 좁았다.

### 22. 승인받은 UI 설계 근거를 구현 후 실측으로 재검증한 것 `[해결 — 딤 처리로 완화]`

- **P** — 방사형 메뉴로 UI를 바꾸는 작업에서, 구현 전 "반지름 R=130이면 캐릭터와 24px 여유가 있다"고 계산해 사용자 승인을 받았다. 이 계산은 **트리거 버튼을 폭 0인 점으로 취급한 근사**였다. 구현을 마치고 실제로 화면을 재검증하니 캐릭터(A)의 실측 화면 폭이 1920 중 x=47~806(42%)로 트리거 위치에 거의 붙어 있었고, 옵션 버튼 15개 전부가 최소 15px에서 최대 145px까지 겹쳤다.
- **A** — 승인된 설계(반지름·각도·트리거 위치)를 다시 흔들지 않고, 먼저 **카메라 투영(`WorldToViewportPoint`) → UI 스크린 좌표 변환**으로 캐릭터의 실제 화면 바운딩 박스를 정밀 실측했다. 이어서 부채꼴의 ±90° 지점이 반지름과 무관하게 항상 트리거 x좌표 근처에 고정된다는 기하학적 성질(`cos(90°)=0`)을 근거로 **"반지름을 아무리 조정해도 구조적으로 해결 불가능하다"**는 걸 수식으로 입증해, 실측치와 함께 그대로 사용자에게 보고하고 처리 방안을 물었다.
- **R** — 사용자가 "겹침 허용 + 휠이 열린 동안 배경을 45% 밝기로 낮추는 딤 처리"를 선택. 이미 확정된 값(반지름·각도·트리거 위치)은 건드리지 않고 두 줄(`ArenaBackground.color` 전환)만 추가해 반영했다. 7개 해상도 회귀(zeroSize=0/overlaps=0/wrapped=0), 하니스 209/209·지문 IDENTICAL 유지.
- **면접 예상 질문** — "승인받은 설계인데 왜 다시 의심했나?" → 승인은 그 시점에 제시된 계산에 대한 승인이지, 계산이 실측과 일치한다는 보증이 아니다. 구현이 끝나 실측이 가능해진 순간, 승인 근거를 검증하는 것은 별개의 책임이다.
- **말할 가치가 있는 지점** — 오류의 근원은 "폭 0인 점" 근사라는 흔하고 그럴듯한 단순화였다. UI 요소는 크기가 있고, 화면에 렌더링된 3D 캐릭터도 자세(이번엔 파이팅 스탠스)에 따라 바운딩 박스가 예상보다 훨씬 넓어질 수 있다 — "표시된 숫자(24px 여유)를 승인받는 것"과 "그 숫자가 실측에서 나온 것"은 다른 문제다.
- 근거 문서: `docs/troubleshooting/radial-menu-clearance-miscalculation.md`, `docs/daily/2026-08-12-radial-menu.md`
