# GripKind enum 값 충돌로 인한 CS8510 (switch 패턴 도달 불가)

작성 2026-08-14 · **상태: 해결**

## 문제 상황

잡기 개편 1차(`GripRevisionGate`) 구현 중 `GripKind` enum에 새 항목
`Lapel`(가슴깃)을 추가하면서 `Dominant`와 같은 정수값 2를 갖게 됐다.
HUD에 손별 그립 상태를 그리는 `GripHandDetail`(LiveMatchPanel.cs)의
switch 식이 `GripKind` 값별로 분기하던 중 `CS8510`(스위치 표현식의
패턴이 도달할 수 없습니다) 컴파일 에러로 즉시 걸렸다.

## 왜 생겼나

`GripKind`가 애초에 "무슨 종류로 잡았나"와 "몇 점짜리인가"를 한 enum에
같이 담고 있었다 — `Dominant=2`가 "우세하게 잡음(2점)"이라는 값 자체의
의미였다. 여기에 잡기 개편이 요구하는 새 목표 종류(`Lapel`=가슴깃)를
추가하면서, 점수 체계를 신경 안 쓰고 다음 빈 번호를 안 쓰고 실수로
기존 `Dominant`와 같은 2를 재사용했다. C# switch 식은 값이 같은 두
분기를 동시에 만족할 수 없는 패턴으로 보고 컴파일 타임에 막는다 —
런타임에 조용히 잘못된 분기를 타는 대신 즉시 실패한 것.

## 시도한 것들

- 처음엔 `Lapel`을 다른 빈 번호로 옮기고 `Dominant`는 그대로 두는 안을
  검토했으나, `GripKind`가 "종류"와 "점수"를 같은 값에 얹어놓은 설계
  자체가 다음 항목이 추가될 때마다 같은 충돌을 반복시킬 걸로 판단했다.

## 최종 해결법

`GripKind`를 순수하게 "무슨 종류로 잡았나"만 나타내도록 재정의하고
(`None, Normal, Dominant, Lapel, BackGrip` — 전부 서로 다른 서수),
"몇 점인가"는 완전히 분리된 조회 테이블 `GripSystem.PointValue(GripKind)`
로 뺐다. 기존 채점 로직이 `Normal=1점`/`Dominant=2점`으로 동작하던 것과
정확히 같은 결과가 나오도록 테이블을 채워, 지문(42노드 스크립트 경로)이
바이트 단위로 그대로 유지됨을 하니스로 재확인했다.

## 재발 방지

이제 새 잡기 종류(예: 향후 확장에서 추가될 목표)를 넣을 때는 `GripKind`에
다음 서수를 이어 붙이기만 하면 되고, 그 항목이 몇 점인지는
`PointValue` 테이블 한 곳에서만 결정한다 — "종류"와 "값"이 같은
enum 안에서 우연히 부딪힐 여지 자체가 없어졌다.

## 이력서 한 줄

enum이 "종류"와 "점수" 두 가지 의미를 한 값에 얹고 있어 항목 추가 시
값 충돌(CS8510)이 재발할 구조였던 것을, 두 책임을 enum과 별도 조회
테이블로 분리해 근본적으로 제거하고 지문 회귀 검증으로 동작 불변을 확인.
