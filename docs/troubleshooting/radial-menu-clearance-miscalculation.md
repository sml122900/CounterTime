# 방사형 메뉴 반지름 승인 계산이 실측과 어긋났다 — 트리거를 점으로 취급한 오류

작성 2026-08-12 · **상태: 해결(딤 처리로 완화, 근본 겹침은 구조상 잔존)**

## 문제 상황

손·코어·하체 선택 UI를 위로 펼치는 드롭다운에서 방사형(휠) 메뉴로 바꾸는
작업이었다. 구현 전 조사 단계에서 "반지름 R=130이면 부채꼴의 오른쪽 끝
(각도 0°)이 화면 x=155 근처에 오고, A 캐릭터의 왼쪽 끝(당시 추정 x≈180)까지
**24px 여유**가 있다"고 계산해 보고했고, 사용자가 "안② 단일호 R=130"으로
승인했다.

구현을 마치고 Play 모드에서 실제로 카메라를 투영(`Camera.WorldToViewportPoint`)해
A·B 캐릭터의 실제 화면 바운딩 박스를 정밀 실측하니 **A는 x=47~806**
(1920 폭의 약 42%)이었다. 승인 근거로 쓴 "24px 여유"는 완전히 틀렸다 —
손·코어·하체 세 축 전부, 옵션 버튼 15개 전부가 A와 겹쳤다. 겹침 폭은
각도 0°(부채꼴이 가장 오른쪽으로 뻗는 지점)에서 최대 145px, 부채꼴의
±90° 끝점에서도 최소 15px이었다.

## 왜 생겼나

사전 계산이 두 가지를 놓쳤다.

1. **트리거 버튼을 폭 0인 점으로 취급했다.** 트리거는 실제로 74px 폭이고,
   옵션 버튼도 74px 폭이다. "반지름 R 지점에 점이 있다"가 아니라 "그 점을
   중심으로 74px짜리 사각형이 있다"로 계산해야 했다.
2. **A의 화면 폭을 감으로 추정했다.** 실측 없이 눈대중으로 잡은 x≈180이
   실제로는 x=47이었다 — 캐릭터가 파이팅 자세(Fight Idle)로 서 있어
   팔다리가 벌어진 `SkinnedMeshRenderer` 바운즈가 단순히 서 있는 실루엣보다
   훨씬 넓다.

더 근본적인 문제는 **부채꼴의 ±90° 지점이 반지름과 무관하게 항상 트리거
x좌표 근처에 고정된다**는 기하학적 성질이었다(`cos(90°) = 0`이므로 각도
성분이 0이 되어 x 오프셋이 사라진다). 즉 R을 아무리 늘려도 ±90° 근처의
옵션은 절대 트리거에서 멀어지지 않는다 — 이 지점만이라도 A의 왼쪽 끝
(x=47)보다 왼쪽에 있으려면 트리거 자체가 x≈10 이하에 있어야 했는데,
트리거는 이미 화면 왼쪽 끝(x=25)에 있어 더 밀 여지가 없었다.

## 시도한 것들

1. 사전 조사 단계에서 반지름 후보별로 "겹침 없음"을 점 근사로 계산해
   보고 → 사용자 승인.
2. 구현 완료 후 Play 모드에서 `Camera.WorldToViewportPoint`로 A·B의
   렌더러 바운즈 8개 꼭짓점을 투영하고, `ArenaBackground`(전체화면
   RawImage)의 스크린 rect로 변환해 캐릭터의 실제 화면 좌표를 얻었다.
3. 손·코어·하체 세 휠을 각각 열어 옵션 버튼들의 실제 `RectTransform`
   월드 코너를 뽑아 A의 실측 바운딩 박스와 겹침 여부·깊이를 계산했다 —
   15개 옵션 전부 겹침, 최대 145px.
4. 반지름을 키워서 피할 수 있는지 검토 — 각도 0° 지점은 반지름을
   늘리면 오히려 더 멀리(오른쪽으로) 가서 A 몸통 안쪽으로 더 깊이
   들어가고, ±90° 지점은 반지름과 무관하게 그대로 겹친다는 것을
   수식으로 확인해 "반지름 조정으로는 구조적으로 해결 불가능"이라고
   결론 내렸다.

## 최종 해결법

승인된 설계(반지름·각도·트리거 위치)를 다시 흔들지 않고, 실측치와
기하학적 불가능성을 그대로 사용자에게 보고한 뒤 처리 방안을 물었다.
사용자가 **"겹침 허용 + 휠이 열린 동안 배경을 딤 처리"**를 선택했다 —
LoL 핑 휠·스파이더맨 웹 기술 휠 같은 참고 사례도 게임 화면 위에 그대로
겹쳐 뜨는 방식이라는 점과 부합한다.

```csharp
// 휠이 열릴 때
_arenaBackground.color = ArenaDim;   // 45% 밝기

// 휠이 전부 닫힐 때
_arenaBackground.color = ArenaBright; // 100% 밝기
```

반지름(손 R=130/코어 R=90/하체 R=100)·각도·트리거 위치는 전부 무수정 —
겹침 자체를 없앤 게 아니라, 열려 있는 동안만 시각적 계층을 명확히 분리했다.

## 재발 방지

- **"여유가 있다"는 주장은 점 근사가 아니라 실제 요소 크기로 계산한다.**
  UI 버튼은 크기가 있다 — 중심점만 비교하면 실제로는 버튼 절반 폭만큼
  틀린다.
- **3D 렌더링된 캐릭터의 화면상 위치는 카메라 투영으로 실측하지, 감으로
  추정하지 않는다.** 특히 자세(Idle이 아니라 파이팅 스탠스처럼 팔다리가
  벌어진 자세)에 따라 바운딩 박스가 예상보다 훨씬 넓어질 수 있다.
- **승인은 그 시점에 제시된 계산에 대한 승인이지, 계산이 맞다는 보증이
  아니다.** 실측이 가능해진 시점(구현 완료 후 Play 모드)에 승인 근거를
  다시 검증하는 것이 책임이다 — 검증 없이 "승인받았으니 끝"으로 넘어가면
  안 된다.

## 이력서 한 줄

> UI 방사형 메뉴 설계를 승인받을 때 쓴 사전 계산(반지름 R=130이면 캐릭터와
> 24px 여유)이 트리거를 폭 0인 점으로 취급한 근사였음을, 구현 후 카메라
> 투영으로 캐릭터의 실제 화면 바운딩 박스를 실측해 발견했습니다. 반지름
> 조정으로는 구조적으로 해결 불가능함을 기하학적으로 입증해 보고하고,
> 처리 방안을 사용자에게 확인받아 배경 딤 처리로 반영했습니다.
