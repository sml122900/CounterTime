# 손 스테이지1 옵션이 "손" 트리거 라벨을 가렸다 — 반지름으로는 못 피하는 방향이 있었다

작성 2026-08-14 · **상태: 해결**

## 문제 상황

`docs/decisions/measured-polar-menu-layout.md`(같은 날 앞선 세션)가 방사형
메뉴 배치를 실측 기반 알고리즘으로 전면 교체하며 "겹침 0 · 화면 이탈 0"을
프로그램적으로 검증했다고 보고했다. 그런데 검증 스크립트가 검사한 것은
옵션 버튼끼리의 겹침과 화면 경계뿐이었다 — **축 트리거 자신의 라벨**은
검사 대상이 아니었다.

사용자가 실플레이 스크린샷으로 손 스테이지1(오른손/왼손/회피, 3항목)에서
"왼손" 옵션이 "손" 트리거 라벨을 그대로 가리고 있다고 신고했다. 겹침 검사에
트리거 라벨을 포함시켜달라는 요청과 함께, 소항목 축이 기술 휠(8항목)처럼
넓게 안 펼쳐지고 세로로 뭉친다는 신고도 같이 왔다.

## 왜 생겼나

트리거 자신이 휠의 원점이다 — `BuildAxisControl`이 "*Control" 앵커의
`anchoredPosition`을 트리거 좌표로 잡고, 그 자식으로 74×36 트리거 버튼을
원점(오프셋 0)에 둔다. 옵션 버튼들은 이 원점을 중심으로 반지름 R, 각도
θ만큼 떨어진 자리에 배치된다.

손 스테이지1은 A 캐릭터 반대편 안전 반원(`arcStartDeg=90`, 아크는 90°~270°)을
쓴다 — cosθ가 0에 가까울수록(90°/270° 근처) x 오프셋이 작아 화면 안전에
유리하고, cosθ가 -1에 가까울수록(180° 근처, 정확히 트리거가 있는 화면
왼쪽 방향) x 오프셋이 커서 위험하다.

그런데 트리거(`TriggerX=55`) 자체가 이미 화면 왼쪽 끝 근처에 있다 —
세이프 마진(10px)을 빼면 45px밖에 여유가 없다. θ=180 방향 항목의 x
오프셋이 세이프 마진을 넘지 않으려면:

```
offset.x = -radius * sin(halfAngle)  (θ=90+halfAngle 부근에서 근사)
```

반지름을 키우면 `halfAngle`(라벨 폭이 필요로 하는 반각)은 작아지지만,
`radius * sin(halfAngle)`은 **반지름과 무관하게 라벨 폭의 절반(halfW)에
점근**한다 — atan2 기반 각도 환산의 성질상, θ=90+halfAngle 근처 항목의
x 오프셋은 반지름이 커질수록 `-halfW`에 수렴할 뿐 그보다 작아지지 않는다.
최소 폭(56px, 반폭 28px) 항목 하나조차 이 점근값(-28px)이 세이프 마진이
허용하는 문턱(-17px, `SafeMargin+halfW-TriggerX = 10+28-55`)을 넘지 못한다.

**즉 이 방향에 놓이는 항목은 어떤 반지름을 골라도, 어떤 배치 알고리즘을
쓰든 트리거와 겹칠 수밖에 없다** — 배치식을 아무리 개선해도 못 푸는
기하학적 한계였다.

## 시도한 것들

1. **1차: 남는 여유를 아크 전체에 고르게 분배**(`TryPackAngles`의 간격
   재분배) — 3항목을 90°~270° 전체에 펼치도록 수정. 재실측 결과 화면
   이탈은 0이 됐지만, 정확히 아크 중앙(θ=180)에 놓인 항목("왼손")이
   여전히 트리거와 겹쳤다. 트리거 검사를 안전 게이트에 추가하지 않은
   채로는 이 겹침 자체를 코드가 못 잡아냈다는 것도 이때 확인했다.
2. 위 계산(반지름별 x 오프셋 점근)으로 "더 나은 펼치기 알고리즘"으로는
   원천적으로 못 푸는 문제임을 증명 — 파라미터 조정을 더 시도하는 대신
   안전 게이트 자체를 바꾸는 방향으로 전환.

## 최종 해결법

**(1) 안전 게이트에 트리거 키프아웃존 추가.** `AllWithinSafeArea`(배치
결과가 화면 세이프 영역 안에 있는지 검사하는 함수)에 트리거 자신의
74×36 박스(원점 중심)와의 AABB 비겹침 검사를 추가했다 — 분리축 판정(x축
또는 y축 중 하나라도 안 겹치면 사각형 전체가 안 겹친다).

```csharp
bool clearsTriggerX = Mathf.Abs(offset.x) > TriggerHalfWidth + halfW;
bool clearsTriggerY = Mathf.Abs(offset.y) > TriggerHalfHeight + halfH;
if (!clearsTriggerX && !clearsTriggerY) return false;
```

이 검사가 실패하면 바깥 재시도 루프(반지름 확대 → 폭 축소)가 다른 조합을
찾는다 — 화면 경계 검사와 완전히 같은 계약.

**(2) 메인 루프가 못 찾으면 쓰는 "마지막 방어선"을 원형 클램프에서 세로
스택으로 교체.** 위 계산이 증명한 대로, 손 스테이지1은 메인 루프(원형 배치)가
사실상 항상 실패해 이 방어선을 탄다. 옛 방어선은 이상적인 각도 위치를 구한
뒤 항목마다 **독립적으로** 화면 안쪽으로 클램프했는데, 여러 항목이 같은
클램프 목표(예: 세이프 마진에 붙은 x)로 동시에 밀리면 서로 겹쳤다 — "실측상
도달하지 않는다"던 이전 세션의 가정이 틀렸다는 걸 이번에 확인.

`FallbackStackedLayout`(신규)이 항목을 입력 순서 앞/뒤 절반으로 나눠
트리거 위/아래 두 세로 밴드(캔버스 세로 1080px 활용, 트리거의 세로 범위는
밴드에서 아예 제외)에 균등 간격으로 쌓는다 — 밴드 자체가 Y축만으로
트리거와 분리되므로 절대 안 겹치고, 같은 밴드 안 항목끼리도 균등 간격이
겹침을 막는다.

**(3) 재검증 중 추가 발견 — 각도 간격만으론 인접 항목 AABB 겹침도 못
막는다.** 전 축을 다시 검사하던 중 하체(4항목)에서 "공격"↔"중립"이 5px
겹치는 걸 실측으로 발견했다 — 각도 간격(`PolarGapDeg`)은 원둘레를 따라
잰 호 길이 여유일 뿐, 접선 방향이 화면 축과 안 맞으면 유클리드 거리가
그보다 작을 수 있다. 안전 게이트에 전 항목 쌍별 AABB 검사도 추가해
해결(재시도 루프가 반지름을 키워 자동 해소).

## 재발 방지

- **"각도 간격을 줬으니 안 겹친다"는 가정하지 않는다.** 원둘레를 따라 잰
  각도(호 길이) 여유는 접선 방향이 화면 축과 안 맞으면 실제 유클리드
  거리보다 클 수 있다 — AABB 겹침은 반드시 직접 계산해서 검사한다.
- **UI 요소가 자기 자신의 원점(트리거)과 겹칠 수 있다는 걸 잊지 않는다.**
  옵션이 트리거를 중심으로 배치되는 구조라면, 옵션-옵션 겹침뿐 아니라
  옵션-트리거 겹침도 같은 안전 게이트에 넣어야 한다 — 둘을 따로 취급하면
  하나를 빠뜨리기 쉽다.
- **"이 반지름으로는 안 되면 더 큰 반지름을 시도한다"는 전략이 항상
  통하지는 않는다.** 원점이 화면 경계에 가까이 있으면, 특정 방향으로는
  반지름을 아무리 키워도 안전 마진을 못 넘는 점근적 한계가 있을 수 있다 —
  파라미터를 몇 번 더 조정해보기 전에, 그 한계가 실제로 있는지 계산으로
  먼저 확인하면 시행착오를 줄일 수 있다.
- **"마지막 방어선"(극단적 경우의 폴백)도 같은 불변식을 지켜야 한다.**
  메인 경로가 겹침 0을 보장해도, 그 경로가 실패했을 때 쓰는 폴백이 같은
  보장을 안 하면 전체 시스템은 여전히 겹칠 수 있다 — 폴백을 "거의 안
  탄다"고 가정하고 대충 짜면 안 된다.

## 이력서 한 줄

> UI 방사형 메뉴에서 옵션이 트리거 자신의 라벨을 가리는 버그를, "더 넓게
> 펼치는 알고리즘"으로는 원천적으로 못 푸는 기하학적 한계(반지름을 키워도
> x 오프셋이 라벨 폭의 절반에 점근해 세이프 마진을 못 넘음)라는 걸 계산으로
> 증명하고, 안전 게이트에 트리거 키프아웃존 + 항목 간 AABB 검사를 추가한
> 뒤 폴백 경로를 원형 클램프에서 겹침이 구조적으로 불가능한 세로 스택으로
> 재설계해 해결했습니다.
