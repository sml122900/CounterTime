## 한 일

### 1. §H 4 — 판정 승격 (MATCH_RULES §E, 실구현)

§4 판정식의 결정론 하한(브래킷)은 무수정 — 그 위에 `PromotionGate`(기본
off, 기존 `BalanceGate`와 같은 "off면 v1 대조 모드와 완전히 같다" 계약)로
감싼 상향 전용 연쇄 롤을 얹었다. `JudgementCalculator.Promote`가 순수
함수로 이 롤을 계산하고(`p = PromoteBase + PromoteSlope×(sum−브래킷하한)`,
링크마다 체인 계수 감쇠, 최대 2연쇄), `MatchEngine.ResolveTechnique`가
Balance의 무득점 드레인은 승격 **전** 하한 기준으로, 승격 롤은 그 다음
`Board.Award` 직전에 배치했다 — 이 순서는 §E.2("Balance changes stay
deterministic")를 문자 그대로 지킨 결과지 임의 선택이 아니다.

승격 결과는 새 이벤트 `JudgementPromoted`로 노출했다 — `JudgementScored`
자체엔 필드를 안 늘렸다. 이유는 2026-08-10 세션의 실패 하나: 그때
`TechniqueId`를 `JudgementScored`에 필드로 추가했다가 42노드 지문이
깨졌다(하니스 덤프가 새 필드를 매 줄에 찍어버려서). 이번 하니스의
`Describe()`는 타입별로 손으로 짠 매핑이라 그 실패가 그대로 재현되진
않는다는 것까지 코드로 확인했지만, 그래도 별도 이벤트 쪽이 더 안전하다고
판단해 그쪽을 택했다.

되치기의 `|sum|` 대칭 적용은 테스트를 "부호 버그가 있으면 반드시 실패하는"
수치로 설계해 고정했다 — 그냥 최종 결과만 검증하는 대신, 부호를 안
뒤집었을 때 나올 값(승격 안 됨)과 뒤집었을 때 나올 값(승격됨)이 다르게
나오는 지점을 골랐다. 상세: `docs/decisions/judgement-promoted-separate-event.md`.

**검증**: 하니스 257 → 269/269(신규 12개), 42노드 지문 IDENTICAL. Unity
MCP `Unity_RunCommand`로 실제 컴파일·실행까지 재확인.

### 2. 이월 로드맵 5개 클러스터 — 계획 문서만 (§H 5/6/7, 훈련 본체, 대련 실행 입력)

각 클러스터에 착수하기 전 실제 코드(`IReadResolver`/`IRecognitionSet`/
`IAdaptationLedger`/`IMasteryStore`/`TrainingSessionController` 등)를
grep·Read로 조사했다. 다섯 다 "동작 0·지문 IDENTICAL·플래그 off를 동시에
만족하는 뼈대"를 짓기엔 실제 걸림돌이 있었다 — 예: §H 6(B의 적응)은
`IReadResolver.For(attacker, a, b)` 시그니처에 기술 id 자체가 안 들어 있어서
인터페이스를 바꿔야 하고, §H 7의 콤보/계단형 성장은 이번에 만든
`Promote()`를 확장해야 하는데 합성 규칙이 아직 없다. 그래서 코드 대신
계획 문서 5개(`docs/plan-*.md`)를 썼다 — 각각 정확한 파일·줄 번호·시그니처,
의존관계, 지문 위험, 사용자 결정 필요 목록을 담았다. 통합 보고:
`docs/overnight-2026-08-13-groundwork.md`.

### 3. 프로덕션 위생 정리 (독립 커밋)

`Assets/_Recovery/`(Unity 에디터 크래시 시 자동 저장하는 씬 복구 스냅샷,
2026-08-12부터 untracked로 존재가 확인됐던 폴더)를 `.gitignore`에
등록했다 — 파일 자체는 안 지웠다, 로컬 캐시라 커밋 대상에서만 뺐다. Active
Input Handling(Both)은 확인 결과 이미 2026-08-11 커밋에 반영돼 있어서
손 안 댐. 그 외 "사람 판단 없이 처리 가능한" 위생 후보는 못 찾았다 —
없는 걸 억지로 만들지 않고 그대로 보고했다.

### 4. 소극 3인(문준배·서도현·오재훈) 차별화 — 코드 조사만

2026-08-13 밤 v3 데이터 수집이 지목한 "가장 안 갈리는 세 상대"를 차별화할
