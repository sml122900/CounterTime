### 2. 인터페이스 면을 의도적으로 좁게 (1·3단계)

`IHabitContext` 를 **4개 멤버로 동결**했다. 각 멤버가 어느 습관 때문에 필요한지 1:1 로 대응한다.

3단계에서 §4 폴백이 "지도수·시계로 가중"을 요구했을 때, 이 면을 넓히는 대신 **별도 인터페이스 `IBrainContext`(6개)** 를 만들었다. 습관 조건이 지도 *개수*나 시계를 보기 시작하면 습관이 상태 평가형 AI 로 흐르고, 그건 설계에서 배제된 안이다.

경계를 **타입으로** 막았다 — `HabitDefinition.Condition` 의 인자가 `IHabitContext` 라 `IBrainContext` 가 들어올 수 없다. 그 위에 리플렉션 테스트를 얹어 (1) 델리게이트 시그니처, (2) `IHabitContext` 멤버가 정확히 넷인지, (3) 폴백 전용 멤버 4개가 거기 없는지를 고정했다. 마지막으로 `IHabitContext` **만** 구현한 객체로 진도윤 습관 조건 3개를 실제 호출한다 — 누가 안에서 캐스팅하면 거기서 터진다.

### 3. 계측이 전제를 깨뜨렸다 (3.5~3.10)

헤드리스 스모크(50교환, A 커밋은 픽스처, B 는 브레인)를 붙이고 수치를 뽑았다. **읽기 사다리 6행 중 1~5행이 전부 0회였다.**

```
=== A varies (4-cycle) ===  [최초 계측]
  turns=33  fallback=29 (87.9%)
  ladder row 1: 0 ... row 5: 0
  ladder row 6: 33            ← 전부 Neutral
```

판정식에서 폭이 가장 큰 항(읽기 −3…+3)이 **통째로 죽어 있었다.** 에러는 하나도 안 났다.

여기서부터 규칙 변경 셋이 나왔고, 전부 문서에 근거 수치와 함께 기록했다.

| 변경 | 근거 |
|---|---|
| 습관 H4 `잡기 노림` 추가 | 초반에 관측될 습관이 하나도 없었다. H1 은 잡기 우위가 필요한데 B 가 거기 못 닿는다 |
| 폴백은 큰기술을 내지 않는다 | 판정의 절반이 폴백에서 나왔다 = 아무도 읽을 수 없는 던지기 |
| 득점 후 그쳐 (`MATCH_RULES` v3.4) | 회복이 그쳐에 묶였는데 그쳐가 경기당 0~2회. 체력이 30교환에 바닥 |

→ `docs/decisions/measurement-driven-rules.md`, `docs/troubleshooting/read-system-silently-dead.md`

### 4. 산술적으로 완주 불가능한 루프 (3.7)

읽기 루프가 이랬다.

- **확정**(수 노트 기록)에는 관측 3회가 필요하고, 원장이 교환 해결 *뒤에* 기록하므로 실효 **4번째 발화**부터 읽힌다
- **폐기**(습관 버리기)는 피해 **2회**면 난다

즉 **A 가 벌줄 수 있는 습관은 읽히기 전에 먼저 사라진다.** 실측에서 H4 가 정확히 그렇게 관측 3회에서 폐기됐다.

처방은 숫자가 아니라 선행조건이었다 — **피해는 A 가 그 습관을 확정으로 안 뒤부터 센다.** 서사도 이쪽이 맞다. B 가 습관을 버리는 건 *간파당했음을 인지*해서인데, 확정 전에는 A 가 읽은 게 없고 B 도 알 방법이 없다. 운 좋은 두 방은 tell 이 아니다.

`RegisterDamage` 가 `bool` 이 아니라 **원장을 받게** 했다. 확정 검사가 안에 있으니 부르는 쪽에 틀릴 자리가 없다.

### 5. 정의와 상태를 타입으로 갈랐다 (2.5)

`HabitDefinition` 이 피해 카운터를 들고 있었다. Unity 의 ScriptableObject 는 **플레이 모드 중 변경이 에셋에 남는** 물건이라, 지난 경기의 폐기가 에러 없이 다음 경기로 따라붙는 구조였다.

`HabitDefinition`·`OpponentDefinition` 을 불변으로 만들고 경기 상태를 `HabitState` 로 뺐다. 테스트로 잡는 것보다 **못 쓰게 만드는 쪽**이 낫다 — 리플렉션 테스트가 두 정의 타입에 쓰기 가능한 공개 필드 0 / 공개 setter 0 을 고정한다.

## 잡은 것 / 틀린 것

### 틀린 진단 둘, 둘 다 계측이 먼저 잡았다

**(1) "2행이 3회 떴는데 유효가 안 났다 — 버그일 수 있다."** 판정식 5항을 그대로 찍어보니 `[0,3,0,1,0] sum=4 → Yuko` 였다. 정상 득점하고 있었다. 폐기가 0회인 데서 거꾸로 추론한 것이었는데 추론이 틀렸다.

**(2) "폐기가 한 번도 안 난다."** 예비 습관 H4b 가 발화하고 있었다 — 예비는 폐기가 나야 점등되므로 **그 발화 자체가 폐기의 증거**였다.

지시가 "고치기 전에 덤프부터"였고, 그게 없는 버그를 두 번 고치는 걸 막았다.

### 테스트 전제가 깨진 것

`RepeatingTheSameCommit_TriggersRowFive_VaryingDoesNot` 이 3.6 이후 실패했다. B 가 잡기를 지향하게 되자 **반복 A 경기가 5교환 만에 끝나** 4번째 동일 커밋이 아예 안 나왔다.

5행이 고장난 게 아니라 테스트가 관찰할 수 없게 된 것이라, 단위 테스트에 5행 커버리지를 남기고 스모크 쪽은 **이번 회귀에서 제일 중요한 감시선**으로 교체했다 — `ReadLadderActuallyRuns_NotEveryTurnIsNeutral`.

### 하니스 함정

`TestContext.WriteLine` 은 리플렉션 하니스에서 `NullReferenceException` 으로 죽는다. NUnit 실행 컨텍스트가 없다. `Console.WriteLine` 은 양쪽 다 된다. 제품 결함이 아니라 하니스 한계다.
