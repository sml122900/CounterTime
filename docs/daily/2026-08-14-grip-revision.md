# 2026-08-14 (밤, 3~8차) 작업 일지 — 잡기 개편 1차

> 같은 날 앞선 세션(`docs/daily/2026-08-14.md`, §H4 + 이월 계획서 + 위생 정리)
> 이후 이어진 별도 작업 묶음. 잡기 개편 1차(MATCH_RULES v4.2 §2b)를 Core
> 엔진부터 UI까지 전부 구현하고, 그 위에서 나온 확인 요청 3건(B 브레인
> 최소 적응, 교환 시간 8초, 자동 공격 조사)과 UI 재작업 1건(휠 라벨 가독성)을
> 연속으로 처리했다. 6개 커밋 전부 하니스 그린 + 42노드 지문 IDENTICAL 유지.

## 한 줄 요약

잡기 체계를 소매/가슴깃/틀어잡기 3종 × 정/교차 + 견고화 + 회피 2존으로
개편했다(`GripRevisionGate`, 기본 off — 기존 스크립트 경로는 바이트 단위
무변경). 구현 직후 사용자가 던진 확인 질문 세 개(B 브레인이 실제로 새
체계를 쓰는가, 교환 시간 8초가 반영됐는가, 자동 공격 버그가 있는가)가 전부
"검증 없이 넘어갔으면 몰랐을" 실제 문제나 재현 불가 사실을 드러냈고, 마지막엔
UI 실측 신고(라벨 겹침·클립)를 받아 배치 알고리즘 자체를 실측 기반으로
다시 짰다.

## 한 일

### 1. Core 그립 해결 매트릭스 (`GripRevisionGate`)

`MatchEngine.ResolveGripExchangeRevised`를 새로 만들어 양쪽 커밋을 동시에
보는 매트릭스(가슴깃 노림=상대 Core 직접 참조, 같은 쌍 맞잡기=코어 조합별
분기, 방어된 존=확률 0)와 교차잡기 롤링 타이머, 견고화(+1)를 얹었다. 기존
`ResolveGrip`(스크립트 경로 전용)은 한 줄도 안 건드리고 게이트 뒤에 완전히
분리해뒀다 — `BalanceGate`/`PromotionGate`가 이미 증명한 "off면 바이트 단위
동일" 계약을 그대로 재사용한 것이다.

구현 도중 `GripKind` enum에 값이 겹치는 두 이름(`Lapel`/`Dominant` 둘 다 2)을
넣었다가 첫 switch 식에서 `CS8510`(패턴 도달 불가) 컴파일 에러로 즉시
걸렸다 — 전 항목을 별개 서수로 바꾸고 "몇 점인가"는 별도 조회 테이블로
분리해 해결. 상세: `docs/troubleshooting/gripkind-enum-value-collision-cs8510.md`.

**검증**: 하니스 269 → 292/292(누적), 42노드 지문 하루 종일 IDENTICAL.

### 2. 손 휠 UI — 4단계 상태기계 + 안전 아크 배치(1차 시도)

`LiveMatchPanel`에 손 축 4단계 상태기계(오른손/왼손/회피/뜯기[2차 예약])를
추가했다. 스테이지1은 A 반대편 안전 반원(cosθ≤0)에 배치하되, 처음엔 고정
각도표(108°/144°/216°/252°, 반지름 70 재사용)로 시작했다가 Play 실측에서
왼손·회피가 각 38.6px씩 화면 밖으로 잘리는 걸 발견해 전용 반지름(40)과
각도(95°/180°/265°)로 재조정 — 회피 하나만 22px 클립을 "딤 처리 전례보다
작다"는 근거로 받아들였다. (이 결정은 6번 항목에서 다시 뒤집힌다.)

### 3. B 브레인 최소 적응 — 조사 후 결손 1건 발견·수정

"B가 새 체계를 실제로 쓰는가" 확인 요청에 코드 추적으로 답했다: 매트릭스·
교차 타이머 적용 자체는 A/B 대칭 구조라 처음부터 자동이었지만, 극단적 방어
습관 둘(H3/서도현 H2)이 회피 존을 안 채워서 새 매트릭스에서 아무것도 못
막고 있었다(진짜 결손). 양소매 기본값을 실어 고치고, 신규 스모크 테스트
(`GripRevisionGateOn_HabitBrainStillCompletesAMatch`, 3프로필×50교환)로 B가
새 체계에서 예외 없이 완주하는 것과 그립 정체로 실제 지도를 받는(비대칭
아님) 것까지 확인했다.

같은 확인에서 "H4 오른소매 노림 → 오른손 정잡기"라는 지시서 예시를 실제
좌표 규칙에 대입해보니 **교차**가 나온다는 걸 발견해 보고만 하고 판단은
안 했다. 사용자가 확인 후 "예시가 작성 오류, 의도는 정잡기 기본"이라고
정정 지시 — B의 소매 잡기 손 매핑을 반전해 정 100%/교차 0%로 재측정
확인했다.

### 4. 교환 시간 8초 — "라이브 전용 ⚙" 자체가 없었다

"교환당 8초 지시가 반영됐는가" 확인 요청에 코드로 답한 결과, `LiveMatchRunner.
SubmitA`가 `ExchangeScript`를 Duration 없이 만들어 클래스 기본값(3초)을 그대로
쓰고 있었다 — 라이브도 지금까지 스크립트 경로와 같은 3초였다. `MatchRulesConfig.
LiveExchangeSec=8`(⚙) 신규 + 배선. 실측으로 잡기·수비·카운터를 순환하는
입력이 정확히 30교환에 정규시간(240초)에 도달하는 것(30×8=240)까지 확인해
배선이 정확함을 숫자로 증명했다.

### 5. 자동 공격 조사 — 재현 실패, 코드 무수정

"코어를 공격으로 유지하면 가끔 자동으로 기술이 나간다"는 신고를 코드
추적(`SubmitA`의 `aAttacks` 게이트, `TechniqueRegistry.Get(null)`의 null
가드)과 두 가지 독립 재현 시도(엔진 직접 호출 15회 루프, 실제 UI 클릭)로
조사했으나 **재현 실패**. 완료 기준이 수정+커밋을 전제했지만, 없는 버그를
지어내는 대신 코드를 무수정으로 두고 정확한 재현 스텝을 요청하는 쪽을
택했다.

### 6. 휠 라벨 가독성 — 실측 기반 극좌표 배치로 전면 교체

2번 항목의 22px 클립 수용이 실플레이 스크린샷에서 "체감상 불가"로 뒤집혔고,
기술 휠(8항목)에서도 라벨 겹침·잘림·뭉침이 새로 신고됐다. 근본 원인은
`RebuildAxisOptions`의 배치식이 항목 수로만 균등분배하고 **라벨 길이를 전혀
안 본다**는 것 — 짧은 라벨은 공간을 낭비하고 긴 라벨은 겹쳤다. TMP
`GetPreferredValues`로 실제 라벨 폭을 재고, 반지름에서의 반각(atan2)으로
환산해 겹침 없이 아크에 패킹하고, 그래도 화면 세이프 영역을 벗어나면
반지름 대신 라벨 폭 상한을 좁혀 재시도하는 알고리즘으로 전면 교체했다.
2번의 고정 각도표는 폐기 — 이제 다른 모든 축과 같은 함수를 쓴다.

프로그램적 쌍별 겹침 검사(`Rect.Overlaps`)로 최대 항목 수(기술 휠 8개)를
포함한 전 스테이지에서 겹침 0·화면 이탈 0을 확인했다.
